1. 为什么在第21课的纯 RTP sip() 之后改 keying

第21课的对端是纯 RTP 音频 SDP：RTP/AVP，没有 a=crypto，也没有指纹。对应配置是未经修改的 sip()，也就是 Connectivity::Sdp × Keying::None。

配方2的对端是 SIP 中继上的 SDES-SRTP。选路仍然用 SDP 里的 c=/m= 地址，但密钥要按 RFC 4568 在 SDP 里用 a=crypto 交换。所以起点还是 sip()，只改一个字段：keying = Keying::Sdes。不要把上一课的纯 RTP 配置直接拿去对接这类中继，也不要改回 webrtc() 或改成 Keying::Dtls——那是另一套指纹和 DTLS 握手，不是本课。

README 把这条写成：“SIP trunk, SDES-SRTP” 从 sip() 起步，然后 keying = Keying::Sdes。旧名 TransportMode::Srtp 也映射到同一写法。出处：README Configuration 配方表第245行，以及迁移说明第255行。

sip() 本身不会替你改 keying，它的预设仍是 Keying::None：

    pub fn sip() -> Self {
        Self::new(
            Connectivity::Sdp,
            Keying::None,
            false,
            RtcpMuxPolicy::Negotiate,
            BundlePolicy::Balanced,
        )
    }

摘自 config.rs 981–989行 @ f1b59bf。注释也写明：Change keying for SDES-SRTP，connectivity for ICE-lite（977–980行）。

2. Keying::Sdes 在 API 和 SDP 里改了什么

枚举定义在 config.rs 171–178行：None 是纯 RTP（RTP/AVP），Sdes 是 SDES、a=crypto（RFC 4568）、RTP/SAVP，Dtls 是 DTLS-SRTP、a=fingerprint、UDP/TLS/RTP/SAVPF。两种等价写法：

let mut config = RtcConfiguration::sip();
config.keying = Keying::Sdes;
let config = RtcConfigurationBuilder::sip()
    .keying(Keying::Sdes)
    .build();

字段赋值见 README 示例第358–360行。Builder 的 .keying(...) 在 config.rs 1222–1225行，RtcConfigurationBuilder::sip() 在 1127–1132行。选路仍是 Sdp，扩展开关、rtcp_mux_policy、bundle_policy 都不因这一步而改。

create_offer（1524–1565行）和 create_answer（1567–1590行）都走进同一个 build_description（5502行）。这里只看和本课有关的两处：

                match keying {
                    Keying::None => section.protocol = "RTP/AVP".to_string(),
                    Keying::Sdes => section.protocol = "RTP/SAVP".to_string(),
                    Keying::Dtls => {}
                }

摘自 5754–5758行。注释写明：SDES-SRTP 必须宣告 RTP/SAVP，好让非 ICE、非 DTLS 的 SIP 中继接受。

当 keying == Keying::Sdes 时，同一函数接着写媒体级 a=crypto（6017–6067行）。offer 的默认值是 tag 1、套件 AES_CM_128_HMAC_SHA1_80、生存期 |2^31、无 MKI；密钥由 generate_sdes_key_params（770–775行）按套件长度生成 inline: 材料。answer 会改用 offer 里选中的套件、tag 和生存期，再写入本端密钥。

RFC 4568 §4 规定：a=crypto 只能出现在媒体级，不能写在会话级，格式为：

# 仅说明格式，密钥是无效占位，不能用于发送或协商
m=audio [port] RTP/SAVP 111
a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:NOT_A_REAL_KEY|2^31

也就是 a=crypto:<tag> <crypto-suite> <key-params> [<session-params>]。密钥写在 SDP 里，是明文材料。RFC 在摘要和适用性段要求：必须另有能提供保密和完整性的协议来保护这份 SDP；在 SIP 里建议用 SIPS URI 或 S/MIME。

DTLS 属性只在 Keying::Dtls 时写入。populate_media_capabilities（6182行) 在 6274–6292行 写明：SDES-SRTP 靠 a=crypto 换密钥，不得宣告 a=fingerprint / a=setup，否则 SIP/SDES 对端（例如 Twilio）会拒绝这份 SDP。PeerConnection::new 在 keying 不是 Dtls 时会跳过证书生成（904–905行）。

4. 答案怎样处理 offer 里的 crypto

RFC 4568 §5.1.2 要求：answer 必须接受 offer 里恰好一条有效的 crypto，并在答案里带回被选中的 tag 和套件，以及 answerer 自己的发送密钥。 §7.1.2 还要求：答案里的主密钥必须与 offer 中的不同。本库在 build_description 的 answer 分支里回显 tag、套件和生存期（6017–6044行），并用本端密钥填充 inline:。

MKI 是例外。negotiate_sdes_mki（887–896行）写明：即使对端 SDP 宣告了 MKI，本端也绝不在发送方向带 MKI。测试 create_answer_srtp_mode_echoes_offer_mki_and_tag 的名称容易读错；它实际断言的是：对 tag 2、套件 AES_CM_128_HMAC_SHA1_32、生存期 2^31、MKI 1:1 的 offer，答案以 2 AES_CM_128_HMAC_SHA1_32 inline: 开头，以 |2^31 结尾，不得以 1:1 结尾。本轮该测试通过。

教学诊断里，对同一形状的 offer（密钥已替换为运行时生成值，不转载上游夹具密钥）得到的脱敏答案行是：

m=audio [port] RTP/SAVP 111
a=sendrecv
a=rtpmap:111 opus/48000/2
a=fmtp:111 minptime=10;useinbandfec=1;stereo=1
a=rtcp:[rtcp-port]
a=crypto:2 AES_CM_128_HMAC_SHA1_32 inline:<redacted>|2^31

阅读要点：tag 变成 2，套件变成 AES_CM_128_HMAC_SHA1_32，生存期仍在，没有 MKI。这份诊断 offer 没有 a=rtcp-mux，所以答案只有 a=rtcp:。官方测试没有断言编解码列表；不要把这里的 PT 111 写成测试已证明的交叉结果。

若诊断 offer 自己不带生存期，答案也就不会回显 |2^31。这与 6043–6044行 只在解析到生存期时才重建 tail 一致。库自己生成的 offer 默认带 |2^31。

re-INVITE 是边界，不是本课主路径。README「SDES Keying」段（268–271行）写明：答案保持我方正在使用的发送密钥，避免对端在通话中丢掉我方音频；对端在同一套件下换新密钥时，在 offer/answer 完成、信令回到 Stable 后再应用；只有套件变化才生成新的本端密钥。本轮两个官方测试通过，分别对应这两点：14401–14470行、14478–14538行。实现上，后一次 offer/answer 若套件相同，会复用上一份本地描述里的本端 key_params（6047–6062行）。这仍不是话机收包证据。

5. 容易误判的边界

  • 不要粘贴真实密钥。inline: 后面是明文密钥材料。公开课文、摘录、证据卡只用无效占位或 inline:<redacted>。上游测试夹具里出现过的密钥，本课不转载。
  • Sdes 不是 Dtls。Keying::Sdes 靠媒体级 a=crypto；Keying::Dtls 靠指纹和 DTLS 握手。本课 SDP 不应出现 a=fingerprint / a=setup。不要把第9–12课的 DTLS-SRTP 路径抄到这里。
  • sip()+Sdes 不是 IceLite。配方2只改 keying，选路仍是 Sdp。配方3才是 sip() 再设 Connectivity::IceLite 与 Keying::Sdes（例如 Linphone）。本课没有把 srtp_mode_ice_lite_answer_has_ice_attributes 当作主路径来跑或来教。
  • re-INVITE：同一套件保持我方发送密钥，套件变了才换新密钥。对端的新密钥在回到 Stable 后才应用。不要把“保持我方密钥”读成“双方密钥都不许变”。
  • 测试通过不等于已经收到媒体。本轮 7 个测试核的是协议、a=crypto 形状和 re-INVITE 密钥策略。没有发送或接收 SRTP 音频，也没有真实话机。Connected 同样不是收包证据。
  • 不要宣称九格都跑过。库称任意 Connectivity 可配任意 Keying；那是库的声明。本课只跑了 Sdp × Sdes 这一格的协商测试。
  • 没有官方示例文件。不要把第21课的 rtp_track_event 改成 Sdes 再当成官方路径。不要为了让某条路径变绿去改上游。
  • 不讲 SIP 信令，不做生产 UA。把 SDP 放进 INVITE / 200 OK 是 rsipstack 和应用的事。SDP 本身还需要另外的安全保护，见 RFC 4568。

6.2 八道自测

先遮住答案。每题都可单独判断，不需要等待聊天回复下一题。八道答案篇幅相同。

第1题

为什么第21课用默认的 sip()，本课要把 keying 改成 Keying::Sdes？

显示第1题答案

sip()默认Keying::None，SDP是RTP/AVP无a=crypto，适合纯RTP。本课要SDES-SRTP，须在sip()后把keying设为Keying::Sdes。不要用纯RTP对接，也不要改回webrtc()或改成Keying::Dtls。

第2题

Keying::Sdes 在 API 和 SDP 上分别改了什么？这份 SDP 会不会出现 DTLS 指纹？

显示第2题答案

从sip()起步以后只改keying为Keying::Sdes，选路字段仍然是Sdp。协商时把媒体协议写成RTP/SAVP，并且在媒体级写入a=crypto。而指纹和a=setup只在Keying::Dtls时才会添加，所以Sdes的SDP里不应该出现这两项。

第3题

怎样写出 sip()+Sdes 的配置？本课的可运行载体是什么？

显示第3题答案

两种写法等价：先调用sip()再设keying为Keying::Sdes，或用Builder的sip().keying(Keying::Sdes)。examples里没有使用Sdes的官方示例。本课可运行的载体是同一提交上的官方库测试，不要为了补示例去改上游。

第4题

本轮在 Linux 教学电脑上跑官方测试，实际证明了什么、没有证明什么？

显示第4题答案

2026年11月27日18:28:22至18:28:23（日本标准时间），在Linux教学电脑上七个官方库测试全部通过，退出码均是0。它们断言了RTP/SAVP、a=crypto存在以及套件前缀。其stdout未打印密钥。这不是已从话机收到SRTP音频的证据。

第5题

回答一条 SDES offer 时，答案会怎样处理 tag、套件、生存期和 MKI？

显示第5题答案

依照RFC4568第5.1.2节和第7.1.2节，答案必须回显选中的标签和套件，并给出自己的发送密钥，且不得复用offer里的密钥。本库还会回显生存期，但故意不回显、也不发送MKI。本轮相关官方测试已经通过；测试名虽含mki，实际的断言却是答案不得带上MKI。

第6题

为什么不能把 a=crypto 的 inline 密钥写进公开课文或证据卡？

显示第6题答案

a=crypto的inline参数是明文密钥材料。RFC4568要求另外用能保密并保护完整性的协议来保护整份SDP；在SIP里建议使用SIPS或S/MIME。课文、摘录和证据卡只用无效占位或inline:<redacted>。切勿把真实或夹具密钥写进公开材料。

第7题

Sdes 是 Dtls 吗？sip()+Sdes 是不是配方3的 IceLite？本课有没有跑完九格？

显示第7题答案

Keying::Sdes靠媒体级a=crypto换密钥，不是靠指纹和DTLS握手的Keying::Dtls。sip()加Sdes只改密钥，选路仍是Sdp，并非配方3的IceLite加Sdes。配方3是下一步，本课未当主路径来教。也不要把九格组合都写成已经跑过。

第8题

re-INVITE 时什么情况下保持我方密钥、什么情况下生成新密钥？测试通过等于收到 SRTP 媒体吗？

显示第8题答案

同一套件的re-INVITE会保持我方发送密钥，并在信令回到Stable之后采用对端的新密钥；只有套件变了才会重新生成新的本端密钥。官方测试已经覆盖了这条边界，仍绝不是真实话机收包证据。测试通过或变成Connected，都不等于已经完成一次SRTP的媒体交换。
