2. 只扩展应用JSON，不重做连接协议

图1是新增应用往返示意，A-1只是纸面编号，不是实际UUID或抓包。两页已经完成原例的连接与应用login。

HTTP /offer仍只负责这例子的SDP交换。chat和ack都走已经打开的数据通道，不是每条消息重发offer，也不是浏览器之间直连。每页到Rust分别有自己的SCTP/DTLS/ICE连接，Rust可以读取并转发应用文字。

应用约定只有下面四种形状。省略号是字段示意，不是可部署密钥或真实捕获值。

路径 应用字段 哪些来自谁
Alice到Rust type=chat、id、content Alice生成id与正文
Rust到Bob type=chat、同一id、sender、content Rust用Alice连接登记名字填sender
Bob到Rust type=ack、同一id Bob接收分支产生
Rust到Alice type=ack、同一id、receiver Rust用Bob连接登记名字填receiver

2.1 Rust枚举把两种消息区分开

下面是新增文件的连续原文。它们是本例应用枚举，不是rustrtc或RFC自带聊天API。

#[derive(Deserialize)]
#[serde(tag = "type")]
enum ClientMessage {
    #[serde(rename = "login")]
    Login { name: String },
    #[serde(rename = "chat")]
    Chat { id: String, content: String },
    // 0018 teaching addition: the receiver page sends this after it has
    // appended the chat text. Rust forwards it and does not create it.
    #[serde(rename = "ack")]
    Ack { id: String },
}

#[derive(Serialize)]
#[serde(tag = "type")]
enum ServerMessage {
    #[serde(rename = "chat")]
    Chat {
        id: String,
        sender: String,
        content: String,
    },
    #[serde(rename = "ack")]
    Ack { id: String, receiver: String },
    #[serde(rename = "system")]
    System { content: String },
}

来源：examples/datachannel_chat.rs:74–100。

Chat.id贯穿往返。Ack不包含正文，也不让浏览器直接提交一个receiver名字。Rust仍只在当前连接已有my_name时处理这些应用消息。名字是任意登记字符串，不是经过账号认证的身份。

2.2 Rust收到chat，不替Bob产生ack

以下是原match中的分支摘录，不能脱离上下文独立编译。

ClientMessage::Chat { id, content } => {
    if let Some(name) = &my_name {
        info!("Client {} forwarded chat id {}", my_id, id);
        let chat_msg = ServerMessage::Chat {
            id,
            sender: name.clone(),
            content,
        };
        let _ = tx.send(InternalMessage {
            sender_id: my_id,
            text: serde_json::to_string(&chat_msg).unwrap(),
        });
    }
}

来源：examples/datachannel_chat.rs:163–176。

Rust保留id和content，用本连接的名字填sender，再放入原有共享广播。日志文字虽然叫forwarded chat，它位于广播调用之前，不是Bob已经接收的回执。应用仍忽略广播发送返回值，不把一行日志当成所有收件人成功。

收到客户端ack才进入另一分支：

ClientMessage::Ack { id } => {
    if let Some(name) = &my_name {
        info!(
            "Client {} forwarded ack id {} receiver {}",
            my_id, id, name
        );
        let ack_msg = ServerMessage::Ack {
            id,
            receiver: name.clone(),
        };
        let _ = tx.send(InternalMessage {
            sender_id: my_id,
            text: serde_json::to_string(&ack_msg).unwrap(),
        });
    }
}

来源：examples/datachannel_chat.rs:177–192。

这次my_name属于发来ack的Bob连接，因此receiver是Bob。这里的sender_id也填Bob内部连接编号。原来的转发过滤就会跳过Bob自己，把ack送到另一页Alice，见同文件130–141行。

本课严格限定同一服务上两个协作页面。没有定向路由表，也没有证明“全部房间成员都收到”。第三页参加时也会收到广播，确认来源和含义就会改变。不要把这个练习包装成多人私聊收据系统。

3. 浏览器如何按id更新那一行

3.1 待确认表只归发送页管理

pending是当前页面的内存Map。它把本页发送的id关联到原文字行和正文，不是Rust服务器的消息数据库。

let pc = null;
let dc = null;
// 0018: ids this page sent and has not yet matched to an ack.
// Cleared on disconnect. Existing lines are left unchanged.
const pending = new Map();

function log(msg, type = 'info') {
    const div = document.createElement('div');
    div.className = 'message ' + type;
    div.textContent = msg;
    chatBox.appendChild(div);
    chatBox.scrollTop = chatBox.scrollHeight;
    return div;
}

function ownLine(content, id, status) {
    return "Me: " + content + "（id=" + id + "）" + status;
}

来源：examples/static/chat.html:57–74。

log返回新建的DOM节点，所以后面可以修改原节点的文字，而不是不断追加“某条消息已确认”的无关行。文字用textContent插入，不按HTML执行。

图2是内存关联示意，不是运行截图。两次正文都一样，完整id才是匹配键。

3.2 发送成功返回后，只写尚未确认

sendBtn.onclick = () => {
    const msg = msgInput.value;
    if (!(msg && dc && dc.readyState === 'open')) {
        return;
    }
    if (!crypto.randomUUID) {
        log("当前浏览器没有 crypto.randomUUID，未发送", "info");
        return;
    }
    const id = crypto.randomUUID();
    try {
        dc.send(JSON.stringify({ type: "chat", id: id, content: msg }));
    } catch (err) {
        log("发送失败，未得到对端确认", "info");
        return;
    }
    const el = log(ownLine(msg, id, "本地已提交，尚无对端确认"), "sent");
    pending.set(id, { el: el, content: msg });
    msgInput.value = '';
};

来源：examples/static/chat.html:200–219。

顺着代码读：检查非空输入与open状态，检查UUID能力，生成id，调用发送；若抛异常就报告发送失败并返回。未抛异常时，才追加本地行并存入pending。它没有在这里宣称Bob已收到。

实际实现用crypto.randomUUID()，不是拿正文做键，也不是复用SCTP通道id0。浏览器若没有该能力，代码只给出提示并停止，不偷偷换一个未验证的生成方法。本课保持本地HTTP入口和已验收浏览器条件，不教改成公网服务。

3.3 Bob先追加文字，再发送应用ACK

以下是接收回调的连续原文，包含chat与ack两个分支。

channel.onmessage = e => {
    try {
        const msg = JSON.parse(e.data);
        if (msg.type === 'chat') {
            log(msg.sender + ": " + msg.content + "（id=" + msg.id + "）", "received");
            if (msg.id && channel.readyState === 'open') {
                channel.send(JSON.stringify({ type: "ack", id: msg.id }));
            }
        } else if (msg.type === 'ack') {
            const item = pending.get(msg.id);
            if (!item || !msg.receiver) {
                return;
            }
            pending.delete(msg.id);
            item.el.textContent = ownLine(
                item.content,
                msg.id,
                "收到" + msg.receiver + "应用确认"
            );
        } else if (msg.type === 'system') {
            log("[System]: " + msg.content, "info");
        }
    } catch (err) {
        log("Raw: " + e.data, "received");
    }
};

来源：examples/static/chat.html:159–184。

chat分支先执行log，才在有id且channel仍open时发送ack。这里的含义是“应用执行了追加DOM文字的路径”，不是检测真人已读，也不保证浏览器已经完成一次屏幕绘制。

ack分支只查本页pending。没有匹配项或没有receiver就返回。有匹配项时，先删除该id，再更新那个节点。相同ACK第二次到达时，pending里已无该项，因此不再修改；未知id也不新增消息行。ack分支没有再发送ack，所以不形成“确认的确认”循环。

这是重复ACK的处理，不是完整聊天去重协议。本例并没有承诺重复chat永远只显示一次，也没有持久化、重试或崩溃恢复。

4. 断开、重连与确认语义

4.1 清空关联，不篡改历史结论

新增文件的Disconnect分支128–146行先清空pending，关闭本连接，然后恢复界面。重新Connect的83行也清空pending。

关闭回调还有一个当前通道判断：

channel.onclose = () => {
    if (dc !== channel) {
        return;
    }
    pending.clear();
    statusDiv.textContent = "Status: Disconnected";
    msgInput.disabled = true;
    sendBtn.disabled = true;
    connectBtn.disabled = false;
    disconnectBtn.disabled = true;
    nameInput.disabled = false;
    log("DataChannel Closed", "info");
};

来源：examples/static/chat.html:185–197。

旧通道若已不是当前dc，该关闭回调不再改当前界面。对于当前通道，清空的是待确认索引，不是DOM里的已有聊天文字。旧行仍写“本地已提交，尚无对端确认”，不擅自改成“对端未收到”。

图3是本例页面状态示意，不是完整网络状态机。断开后的旧行不参与新会话的pending匹配。

4.2 用准确句子描述这个ACK

已观察的证据 可以支持 不能单凭它支持
本页出现带id的Me行 本地发送路径执行到显示和登记 Rust解析成功或Bob已追加文字
Rust记录对应chat分支 该连接解析并进入chat处理分支 Bob收到、所有广播消费者发送成功
Bob页显示对应id与正文 Bob应用执行了该条文字追加 Alice已经收到ACK
Alice原行匹配ACK并更新 在两个协作页面按本协议运行前提下，Bob的应用确认已经返回 真人已读、落盘保存、现实身份或未来不丢
一直没有ACK 尚未得到应用确认 消息一定丢失、Bob一定没收到

receiver来自Rust当前连接登记的名字，不代表该名字经过认证。恶意客户端可以虚构应用ACK；这不是防伪的交付证明。Rust是两条DataChannel的端点，可读明文应用消息，不能说Alice到Bob做了端到端加密。

4.3 不要把三种“确认”混在一起

本课JSON type=ack是我们新增的应用协议，确认特定id的处理路径。SCTP传输确认属于底层传输机制，不替代应用显示证据。DCEP的DATA_CHANNEL_ACK用于建通道握手，不是在确认某条chat。

协议分层见RFC8831 §1，用户数据传输见§6.6。带外约定见§6.5，DCEP对照见RFC8832 §5.2。本例仍用双方预先约定的negotiated chat/id0，不因新增应用ACK而改发DCEP握手。

实际测试 观察到的事实 结论边界
双向ACK Alice与Bob的各自原行分别得到对方确认 这轮两个方向都通过
相同正文不同id 先释放第一条ACK，仅第一行确认；再释放第二条后第二行确认 按id而非正文匹配
暂缓ACK再释放 Bob已有pause-check，Alice仍未确认；释放后才确认 对方显示和确认返回是两件事
重复与未知ACK Alice的ACK接收数1变3，发送数始终0；Me仍一行 没有误匹配或ACK回环
断开后新会话 pending-left旧行保持未确认；after-reconnect新id得到确认 不把旧待确认项带入新会话

暂停只发生在云端测试脚本的send包裹24–89行，普通页面没有暂停按钮。它拦住特定应用ACK发送，没有关闭DataChannel。上面的约0.5秒是受控测试等待，不是网络延迟、RTT或性能测量。

重复未知ACK的计数来自测试279–318行。正常确认后，Bob又发送重复ACK与未知id；Alice确实多收到两条，但没有回发ACK。不是仅凭“没看见刷屏”下结论。最后的无暂停复测367–387行使用final-a/final-b，两边各自确认。

5.2 三个排错场景

下面是结合已验证机制的排查题，不是声称所有读者故障都已复现。

场景A：启动成功，但发送后只有旧Me，没有id。先查是否仍是原例。核对补丁、两个改动文件、服务二进制和重新加载的页面。根HTML编译时嵌入，不能只保存HTML却继续用旧服务。保持两页都使用同一新版，不混用旧标签页。

场景B：Bob确有对应id，Alice一直未确认。已知chat到Bob应用，未知的是ACK产生、返回和Alice匹配。按“Bob的chat分支是否发ACK、Rust是否收到ACK、Alice是否收到且pending仍有该id”找证据。不要说“没确认所以没收到”，也不要因这一现象重做offer或关DTLS。

场景C：同一正文有两条，或者重连后收到旧ACK。先比较完整id和当前会话。匹配逻辑只查pending；相同正文不能替代编号。已确认项被删除，断开也清空，旧ACK不能因此改写旧行。这是新增本地关联规则，不是持久化送达协议。

Windows、第三页、多网络、公网、音频、鉴权、持久保存和自动重试都没有因此验收。实际Linux测试成功不等于你的Windows已成功，也不等于已经学会实现。

6.2 八道自测

一次答完后，再分别展开答案。不需要逐题等聊天回复。

题1：代码从哪里来

只克隆固定版rustrtc并运行原例，为什么还不会出现接收确认？下载包解压后应在哪个目录执行cargo？

题1参考答案

原例没有id和ack字段。本课须向新克隆应用下载包里的两个文件补丁。cargo在包含上游Cargo.toml的rustrtc仓库根目录执行，不在解压包目录。打补丁后重新编译，并重新加载两页。

题2：画出同一个id

Alice发chat到最终原行更新，中间哪一端产生id，哪一端产生ack？Rust在收到chat时能自己生成这条“Bob应用确认”吗？

题2参考答案

Alice生成id，Rust把它随chat转发。Bob在解析并追加文字后产生同id的ack，Rust收到后填Bob登记名字并转发，Alice按id更新原行。Rust不能用收到chat代替Bob的应用处理确认。

题3：相同正文怎样区分

pending有id-A与id-B，两项正文都为same-body。只收到id-A的ACK，应该改哪行，删哪项？为什么不能按正文匹配？

题3参考答案

只改id-A关联的DOM行并删id-A，id-B仍待确认。正文可以重复，不表示是同一次发送；完整id才关联这条消息。代码不按最后一行或显示名字猜测。

题4：重复ACK与未知ACK

正常确认后再收到同id的ACK，随后又收到未知id的ACK，为什么不应多出chat行或不断发送新的ACK？

题4参考答案

第一次确认已经删除pending项。重复或未知id查不到item便返回，不新增chat行。ACK处理分支只匹配更新，不发送ACK，因此不发生确认循环。这不等于已经实现重复chat去重。

题5：没确认能说明丢了吗

Bob已显示pause-check，Alice仍“尚无对端确认”。能断言Bob没收到吗？测试暂停了哪层，能把两日志间隔当网络RTT吗？

题5参考答案

不能，Bob显示本身已支持应用收到并追加。云端脚本暂缓的是应用ACK的send，不是断开底层通道。间隔包含人为等待，不能当网络RTT或性能数字。尚无ACK只表示尚未得到确认。

题6：断开后的旧行

Alice带未确认消息断开，重连后收到旧id的ACK，旧行应该怎样？清空pending是否等于删聊天记录或判定对端未收？

题6参考答案

旧行保持未确认。断开清空的是当前连接的待确认关联，旧ACK无匹配项，不改旧行。它没有删除DOM文字，也不能推断Bob未收；新会话用新id建立新关联。

题7：谁是receiver

ACK里的receiver由哪里填？“收到Bob应用确认”能证明Bob的现实身份、真人阅读、落盘保存或端到端加密吗？第三页能直接参加这课验收吗？

题7参考答案

Rust从发来ACK的连接已登记名字填receiver。名字没有认证；协作页面追加DOM不证明真人阅读或保存。Rust能读转发内容，不是浏览器间端到端加密。该广播练习只按两个协作页面验收，不能直接扩大为多人保证。

题8：三种成功不要混同

本课JSON ACK、DCEP的DATA_CHANNEL_ACK与DataChannel open各说明什么？Linux五组全过后，还不能替用户声称哪些条件已经验证？

题8参考答案

JSON ACK确认特定消息的应用路径。DCEP ACK属于建通道握手，本例预协商通道不靠它。本端open是通道状态，不是特定chat处理证据。云端Linux成功不证明用户Windows、公网、第三页、音频或生产级安全与持久投递通过。
