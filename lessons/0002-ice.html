巩固 ICE：从候选到选中的那一对

十分钟看完候选类型、优先级、ufrag/pwd、检查和提名。每一步对到提交 e13b5f2 的源码，并看一段刚跑出来的日志。

1. 先对一下

第 1 课的地图还在：信令（HTTP / SIP）在栈外交换 SDP；ICE 只负责找出一条能通的 UDP 路，不加密。下面按「候选 → 优先级 → 凭证 → 检查与提名」把 ICE 补扎实。

2. 候选类型

RFC 8445 定义四种类型。采集阶段会出现前三种里的 host，以及（配了服务器时的）srflx 和 relay；prflx 是检查过程中才发现的。

优先级公式

源码和 RFC 是同一个式子（priority_for，:4856–4866）：

priority = (type_pref << 24) | (local_pref << 8) | (256 - component)
// UDP 的 local_pref 固定 65535；component 1 是 RTP（rtcp-mux 时也只用 1）

host + component 1 算出来是 2130706431。下面真实 offer 里就能看到这个数。

候选对还有自己的优先级（IceCandidatePair::priority，:5022–5029；G 是 controlling 那端的候选优先级，D 是 controlled 的）：

pair_priority = 2^32 * min(G, D) + 2 * max(G, D) + (G > D ? 1 : 0)

RFC 8445 §5.1.2.1、§6.1.2.3。

3. SDP 里的凭证和候选

我在共享电脑上跑了 playground/ice_loopback：两台 PeerConnection::webrtc()，等收集完成再交换 SDP（不是 Trickle）。offer 里的 ICE 行是：

m=application 9 UDP/DTLS/SCTP webrtc-datachannel
a=ice-ufrag:1c956ee891287fc5
a=ice-pwd:53bd5b188e745d32657e274f751fa50e
a=candidate:42c85eb97134975e 1 udp 2130706431 172.30.0.2 41795 typ host
a=candidate:2d593ec349bdb740 1 udp 2130706431 172.17.0.1 34716 typ host
a=end-of-candidates

这几行从哪来：

  • ice-ufrag / ice-pwd 来自 IceParameters::generate（:5051）：ufrag 是 8 字节随机数的十六进制（16 个字符），pwd 是 16 字节（32 个字符）。写进 SDP 在 src/peer_connection.rs:5819–5822，值从 ice_transport.local_parameters()（同文件 :5623）取出。
  • 收集完成后不再写 a=ice-options:trickle，而是写 a=end-of-candidates（:5823–5841）。这是 vanilla ICE：对端不必再等后续候选。Trickle 时用 PeerConnection::add_ice_candidate（:4293），它转给 IceTransport::add_remote_candidate（mod.rs:2104）。

STUN Binding 请求里的 USERNAME 是 远端ufrag:本地ufrag，MESSAGE-INTEGRITY 用远端的 pwd 算（perform_binding_check，:4147–4165）。RFC 8445 §7.2.2。

4. 角色、检查、提名

谁发 offer，谁就是 controlling：create_offer 在两边都还没有 local/remote description 时调用 set_role(IceRole::Controlling)（src/peer_connection.rs:1538–1541）。answerer 默认 Controlled（:1574–1585）；对端是 ICE-lite 时除外，full 的一方必须当 controlling。

两边都有远程凭证和对方候选之后，perform_connectivity_checks_async（mod.rs:2227）把本地×远程配成 IceCandidatePair（:5007），再对每一对做 STUN Binding 检查（perform_binding_check，:4106）：

let mut msg = StunMessage::binding_request(tx_id, Some("rustrtc")); // stun.rs:22
msg.attributes.push(StunAttribute::Username(format!("{}:{}",
    remote_params.username_fragment, local_params.username_fragment)));
msg.attributes.push(StunAttribute::Priority(local.priority));
// controlling → IceControlling(tie_breaker)；nominated 时再加 UseCandidate
// controlled  → IceControlled(tie_breaker)
let bytes = msg.encode(Some(remote_params.password.as_bytes()), true)?;

成功的一对进入有效列表。controlling 等 nomination_grace（默认 200 ms，src/config.rs:703、1019）后调用 nominate_best_pair（:2711）：按对优先级排序，再发一条带 USE-CANDIDATE 的 Binding（:2785，属性定义在 stun.rs:103）。controlled 收到后跟随（:3964–3970），必要时代替先选中的临时路径。选中的那一对经 commit_selected_pair（:2687）发布。RFC 8445 §6.1.4、§7、§8；STUN 报文见 RFC 8489。

6. 何时需要 TURN

host 和 srflx 都检查失败时，才走 relay。两边都在对称 NAT 后面、或防火墙把直连打掉，是典型场景。配置是 ice_servers 里加 turn: / turns: URL，并带用户名口令（IceServer，src/config.rs:34）。IceTransportPolicy::Relay（:85）会强制只用中继。采集入口是 gather_servers（mod.rs:6022）。RFC 8656 §3。
