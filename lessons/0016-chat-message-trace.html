2. 先分清三处使用的“消息”

图 1 是本例的代码处理路径示意，不是日志，也没有表示各步耗时。前提是双方数据通道已打开，并已完成本例的应用名字登记。

先把各类数据归到对应位置：

  • HTTP 信令请求：{"sdp":"此处省略描述"} 发给 /offer。这是教学占位，不是可用 SDP。它负责这一例子的描述交换，不是聊天正文。
  • DataChannel 应用消息：例如 {"type":"login","name":"Alice"} 或 {"type":"chat","content":"L16-R1-A1"}。它们走已经建立的数据通道。
  • Rust 进程内广播项：有 sender_id 和 text 两个字段。text 保存序列化后的服务端 JSON。这个内部结构体本身不是直接发给浏览器的 JSON。

HTTP 请求及路由见 examples/static/chat.html:109–116、examples/datachannel_chat.rs:46–50。内部 InternalMessage 定义见 examples/datachannel_chat.rs:24–28。后面的发送代码会进一步证明为什么只发其中的 text。

这里的 type: "chat" 是示例自定的 JSON 字段，不是 SDP 媒体类型，也不是 DTLS 消息类型。浏览器与 Rust 约定如何解释这段字符串；DataChannel 不替应用解释“聊天”和“登录”。

3. Alice 的发送按钮做了两件不同的事

下面是原浏览器文件的连续摘录。你不需要把它另存成一个新页面。

sendBtn.onclick = () => {
    const msg = msgInput.value;
    if (msg && dc && dc.readyState === 'open') {
        const payload = JSON.stringify({ type: "chat", content: msg });
        dc.send(payload);
        log("Me: " + msg, "sent");
        msgInput.value = '';
    }
};

来源：examples/static/chat.html:171–179。

当输入是 L16-R1-A1，应用构造的 JSON 等价于：

{"type":"chat","content":"L16-R1-A1"}

这是按源码推演的字段示意，不是捕获的网络字节，也不承诺空格或字段顺序。注意两点：

  1. 客户端这个 chat 对象没有 sender。Alice 的名字不是发送按钮在这里拼进去的。
  2. dc.send(payload) 之后紧接着调用本地 log("Me: " + msg, "sent")。这条显示没有等待 Bob 的应用回执。调用若抛错也不会正常执行到后面的显示，因此 Me 既不是“完全没执行任何发送”，也不是“另一页已收到”。

log 在这里创建并追加页面文字，见 examples/static/chat.html:60–66。你可以在源文件中同时圈出“发送”和“本地显示”，不能把两处当成同一份接收证据。

4. login 给当前连接登记名字，不是握手消息

浏览器在通道打开回调里自动发送 login，不需要你再找一个 Login 按钮：

channel.onopen = () => {
    statusDiv.textContent = "Status: Connected";
    msgInput.disabled = false;
    sendBtn.disabled = false;
    disconnectBtn.disabled = false;
    log("Connected as " + name, "info");

    // Send login message
    channel.send(JSON.stringify({ type: "login", name: name }));
};

来源：examples/static/chat.html:138–147。Connected as Alice 在调用 login 发送之前就已被本页写出来，所以这行也不是 Rust 确认名字登记成功的应用回执。

服务端为这次连接创建的任务，初始有 my_name: Option<String> = None，见 examples/datachannel_chat.rs:113–118。解析到 login 后才给它赋值：

ClientMessage::Login { name } => {
    my_name = Some(name.clone());
    info!("Client {} logged in as {}", my_id, name);
    let sys_msg = ServerMessage::System {
        content: format!("{} joined the chat", name),
    };
    let _ = tx.send(InternalMessage {
        sender_id: my_id,
        text: serde_json::to_string(&sys_msg).unwrap(),
    });
}

来源：examples/datachannel_chat.rs:142–152。上面的 ClientMessage、ServerMessage 是示例自己的应用枚举，不是 rustrtc 的握手类型。定义见 examples/datachannel_chat.rs:74–90。

这里的名字只是应用接收并保存的字符串，不证明现实身份。login 不是 ICE ufrag/pwd、证书校验或 DCEP OPEN。第 15 课已解释通道的预协商方式，本课不重新展开。

Bob 的 login 会产生一条 system 消息供其他客户端显示。Alice 看到 [System]: Bob joined the chat，能支持本例相关通知已到 Alice；它不能替代 Bob 收到 Alice 某条 chat 的证据，方向和消息都不同。

5. Rust 收到字节后，重新构造服务端消息

先认清应用枚举的字段。下面是原 Rust 文件的连续摘录：

#[derive(Deserialize)]
#[serde(tag = "type")]
enum ClientMessage {
    #[serde(rename = "login")]
    Login { name: String },
    #[serde(rename = "chat")]
    Chat { content: String },
}

#[derive(Serialize)]
#[serde(tag = "type")]
enum ServerMessage {
    #[serde(rename = "chat")]
    Chat { sender: String, content: String },
    #[serde(rename = "system")]
    System { content: String },
}

来源：examples/datachannel_chat.rs:74–90。#[serde(tag = "type")] 让应用用 type 字段区分分支。客户端 Chat 只有 content；服务端 Chat 另有 sender。这里的两个 Chat 不是同一个 Rust 类型。

接收入口的分支开头是：

Some(DataChannelEvent::Message(data)) => {
    if let Ok(msg) = serde_json::from_slice::<ClientMessage>(&data) {

这只是原 match 分支的开头，不是可独立编译的完整程序。来源：examples/datachannel_chat.rs:137–141。DataChannelEvent::Message(data) 和 recv 的定义见 src/transports/datachannel.rs:116–124、247–250。

通道消息到达还要符合应用解析规则。解析成功得到 ClientMessage 后，chat 分支继续执行：

ClientMessage::Chat { content } => {
    if let Some(name) = &my_name {
        let chat_msg = ServerMessage::Chat {
            sender: name.clone(),
            content,
        };
        let _ = tx.send(InternalMessage {
            sender_id: my_id,
            text: serde_json::to_string(&chat_msg).unwrap(),
        });
    }
}

来源：examples/datachannel_chat.rs:153–164。逐行只问三个问题：有没有登记名字？sender 从哪里取？序列化的完整对象是什么？

图 2 把同一个教学标记的字段变化放在一起。图中的对象是逻辑值示意，不是抓包。内部行也不是让你部署的新 JSON 协议。

所以 Rust 不是原样转发客户端那段 JSON。它为服务端消息加上已登记的 sender，再把新消息序列化放入内部广播。sender_id 用来控制进程内转发；它不是发到浏览器里的 sender 字符串，也不是消息序号。

正常页面会先发 login。本课纸面分析还应看见一个边界：假设某个自定义客户端没登记名字就发 chat，if let Some(name) 不会进入广播块。这是源码条件推演，不是本课注入非法消息做了实测。

6. 一个接收任务，加上每个连接自己的转发任务

下面摘录的是当前连接的广播转发任务，不是收到 Alice 数据就直接调用 Bob 页面代码。

let sender_task = tokio::spawn(async move {
    while let Ok(msg) = rx.recv().await {
        if msg.sender_id != my_id
            && let Err(e) = pc_sender.send_text(0, msg.text).await
        {
            warn!("Failed to send data to client {}: {}", my_id, e);
            break;
        }
    }
});

来源：examples/datachannel_chat.rs:122–131。每个 offer 各自创建连接和 id，并订阅共享广播，见 examples/datachannel_chat.rs:94–115。

图 3 是两个页面时的任务关系示意，不是线程或网络数据包的固定执行顺序：

最容易看反的是 my_id。在 Alice 的转发任务里，它是 Alice 这次连接的编号；在 Bob 的转发任务里，它是 Bob 的编号。同一广播项的 sender_id 则仍表示原发送连接。

本例按连接编号排除发送者，不按用户名字符串排除。两个连接若取同名，名字会让人看不清，但这个过滤条件不会因此把它们合成一个连接。练习仍用 Alice、Bob，避免观察歧义。

send_text(0, msg.text) 的第一个参数是该连接里的通道 id。两个连接都能用 0，不表示这是全局“房间 0”，也不是 TCP/UDP 端口。发送入口定义见 PeerConnection::send_text，src/peer_connection.rs:4201–4210。

这里实际发送的是 msg.text，即序列化的服务端 JSON。内部结构体的 sender_id 没有作为第二份 JSON 包裹一起发出。应用广播也不保证所有订阅者已经读到、解码或显示。本课不扩展队列积压、重试和背压实现。

7. Bob 还要解析并显示，收到不等于显示

浏览器接收回调原文如下：

channel.onmessage = e => {
    try {
        const msg = JSON.parse(e.data);
        if (msg.type === 'chat') {
            log(msg.sender + ": " + msg.content, "received");
        } else if (msg.type === 'system') {
            log("[System]: " + msg.content, "info");
        }
    } catch (err) {
        log("Raw: " + e.data, "received");
    }
};

来源：examples/static/chat.html:148–159。

纸面输入 {"type":"chat","sender":"Alice","content":"L16-R1-A1"} 时，回调解析对象，再把 sender、冒号和 content 拼成页面文字。你看见的 Alice: ... 不是网络层自动添加的，也不是 SDP 的字段。

三个判断要分开：

  • 通道把数据交给 onmessage。
  • 应用成功解析，并选中了 chat 或 system 分支。
  • 页面追加了你要找的本轮标记。

例如，纸面输入未加 JSON 引号的 hello，JSON.parse 会失败，按此回调进入 catch，尝试显示 Raw: hello。这是源码推演，不是本轮收到过这个坏消息。一般看到 Raw 只说明 try 块内发生异常，不能不查内容就认定是 ICE 失败，或断言所有 Raw 都只来自语法错误。

再看一个纸面对象 {"type":"notice","content":"L16-R1-A1"}。它是合法 JSON，但本回调没有 notice 分支，也不会仅因 type 未识别而自动抛错。因此“合法 JSON”“符合此应用约定”“页面显示”是三件事。

协议只在这里补一条边界：DataChannel 使用 SCTP 消息服务，这些应用消息并不是每条都对应一个 UDP 数据报，底层可以分片。也不能把一次 DataChannelEvent::Message 当作直接从 UDP socket 读到的一包。依据：RFC 8831 §5、§6.6。这不改变本课在应用消息层逐项追踪的做法。

8. 源码追踪不是示例自带的逐步日志

第 15 课已有的云端成功证据，是两个页面收到对方的 hello-from-alice / hello-from-bob，并记录通道打开与名字登记。那不是今天新跑出的 L16 标记记录，更不是你的 Windows 运行结果。

当前例子的相关日志记录 open、login、close 和部分错误，没有在上面每条 chat 的各个处理节点都写 INFO。相关分支见 examples/datachannel_chat.rs:137–174。设置 RUST_LOG 不会凭空增加源码没有写出的逐步聊天日志。

填写证据卡时分两栏，不把推演写成观察：

项目你实际观察什么单凭它不能推出什么
发送页的 Me 加本轮标记发送代码执行到本地显示Rust 已解析、Bob 已显示
Rust 的 login 日志相应连接执行了名字登记分支后续每条 chat 都已送达
Alice 看见 Bob joined 通知该通知在 Alice 页显示Bob 已收到 Alice 的 chat
Bob 显示 Alice 加本轮唯一标记本例该次应用内容已到 Bob 并显示全部未来消息不丢、音频可播放
源码推演出的服务端 JSON代码预期构造的字段已经抓到了这份实际网络数据

这一层的 DataChannel 数据走 SCTP/DTLS，不是 SRTP 音频，也不是每发一句重做一次 SDP。只需复习 RFC 8831 §1 的分层；握手、证书和音频调试本节不展开。

9. 三种现象，先写缺哪条证据

只有 Me，没有 Bob 的接收文字

先确认 Bob 当前是否连接、有没有使用本轮独有标记、查看的是不是正确页面。再按“Rust 接收、解析、名字、广播、Bob 转发、Bob 解析显示”列未知项。没有服务端逐条 chat 日志时，不凭日志安静就断言 Rust 没收到。

本课不要求你添加日志代码，也不让你改协议碰运气。先交现有页面状态、终端真实错误、标记和具体缺失现象。如果这些证据仍不足，下一次再设计一个小的受控验证任务。

Bob 看到 Raw，或合法 JSON 没有显示

按第 7 节检查应用解析和类型分支。Raw 表明回调拿到过数据并在 try 内遇到异常，不是“完全没数据”的同义词。合法但未处理的 notice 对象，又不同于解析失败。

这两个都是分析场景，不要求你在控制台构造或注入消息。不要因为应用 JSON 不匹配就关掉 DTLS 验证、改用纯 RTP，或重新收集 ICE 候选。

Bob 已断开，Alice 仍能在本页写出 Me

浏览器的 Disconnect 处理会关闭该页连接/通道、显示 Disconnected 并禁用发送，见 examples/static/chat.html:119–135。它并不把 Alice 的 Me 变成 Bob 收件回执。

如果 Alice 自己的通道仍 open，Alice 的本地发送路径仍可能执行到 Me。不要由此宣布 Bob 已收到或“广播自动补送成功”。也不要给服务端的 left 通知承诺固定出现时间。新断开场景在本课未实测。

10. 不改代码的实践：交一张消息字段卡

先保证两个页面已 Connected。把 R1 换成本次未用过的短代号。只发教学标记，不发真实个人信息。

  1. Alice 发送 L16-R1-A1。记录 Alice 页的 Me 与 Bob 页带 Alice 署名的同一标记。
  2. Bob 回复 L16-R1-B1。这次必须在 Alice 页找到 Bob 的署名和标记。第一步成功不能替代反向观察。
  3. 不运行新代码，按正文写出 A1 的客户端 JSON、服务端 JSON、内部广播项各有哪些字段。把这些填在“源码推演”栏。
  4. 对照两个页面实际出现的文字，把“页面观察”栏补齐。没出现就写没出现，保留真实报错，不把预期抄成结果。
  5. 可选观察：Bob 点击 Disconnect。等它显示 Disconnected 后，若 Alice 自己仍 Connected，再发一个全新 A2 标记。只记录实际结果，不要求立即看见 left，不把“另一页没收到”的观察泛化成所有网络断开机制。

第五步是留给你的新观察任务，课前没有对这个新标记/断开场景做验收。不会改动源程序；如果 Alice 也已经关闭，就不要为了制造 Me 而绕过页面状态检查。

卡片只需写六行：

  • 本次源码 SHA 与教学标记。
  • 客户端 chat JSON 的字段。
  • sender 名字在 Rust 哪里取得。
  • InternalMessage 的 text 保存什么，sender_id 用来做什么。
  • 发送页与接收页实际看见的文字，注明方向。
  • 一条已经支持的结论，以及一条仍未知的结论。

11. 八道自测

先一次答完，再展开各题答案。下面都是简答，没有通过选项长度提示答案。

  1. Alice 发 A1 时，客户端 chat JSON 包含 sender 吗？Bob 看见的 Alice 字符串由谁加入，取自哪里？
  2. Connected as Alice 为什么还不能当 Rust 已处理 login 的确认？login 是哪层协议？
  3. Rust 的 ClientMessage::Chat 和 ServerMessage::Chat 分别有哪些字段？收到通道消息后，如果应用解析不成功，能直接跳到正常 chat 广播吗？
  4. 转发 send_text(0, msg.text) 时，发的是纯 content、完整服务端 JSON 字符串，还是整个 InternalMessage？0、sender_id、sender 分别表示什么？
  5. Alice 的消息进入共享广播后，为什么 Alice 的转发任务跳过，而 Bob 的转发任务发送？如果两人名字相同，过滤条件会变吗？
  6. 纸面输入未加引号的 hello 与 {"type":"notice","content":"A1"}，在 Bob 的回调中分别怎样处理？Raw 能直接证明 ICE 没通吗？
  7. Alice 看见 Me: A1 和 Bob joined 通知，足够证明 Bob 收到 A1 吗？哪条额外观察才能支持本例的这个结论？
  8. 某人说“没看到逐条聊天 INFO，所以 Rust 一定没收到；DataChannel 的一条 JSON 就是一包 UDP；这次聊天成功也证明音频能播放”。逐项指出依据缺在哪里。

参考答案

第 1 题参考答案

没有，客户端 chat 只发 type 和 content。Rust 在该连接的 chat 分支读取 my_name，填到服务端 Chat 的 sender，再序列化转发。

第 2 题参考答案

浏览器在发送 login 之前先写了 Connected as。这只反映本地回调推进，不是 Rust 的应用确认。login 是聊天应用登记名字，不是 ICE、DTLS 或 DCEP。

第 3 题参考答案

客户端 Chat 有 content，服务端 Chat 有 sender 和 content。应用按 type 解析为 ClientMessage。解析不成功不进入该正常匹配/广播块；通道收到字节不保证应用接收成功。

第 4 题参考答案

发的是 msg.text 中的完整服务端 JSON 字符串。0 是当前连接的通道编号；sender_id 是内部原发送连接编号；sender 是给页面显示的已登记名字。InternalMessage 包装不直接发给浏览器。

第 5 题参考答案

Alice 任务的 my_id 等于该广播项 sender_id，所以跳过。Bob 任务的 my_id 不同，所以进入发送条件。比较的是连接编号而不是名字，两人同名不改变此条件。

第 6 题参考答案

hello 在 JSON.parse 处失败，按纸面代码进入 catch 并尝试显示 Raw。notice 对象能解析，但本例没有相应显示分支，不自动因未知 type 抛错。Raw 不是 ICE 未通的证明。

第 7 题参考答案

不足。Me 是本地追加，Bob joined 是不同方向、不同消息的通知。应在当前 Bob 页面实际看到 Alice 加本次唯一 A1 标记，不能用旧文字代替。

第 8 题参考答案

示例未为每条 chat 的每个节点写 INFO，日志缺席不足以判定没接收；SCTP 消息可在底层分片，不能一一对应 UDP；聊天应用接收不验证音频的 SRTP、解码或播放。都应找对应层的证据。

12. 间隔复习与主读来源

明天遮住正文，画三样东西：客户端 JSON、内部广播项、服务端 JSON。用箭头标出是谁添加 sender、在哪一层过滤发送者。隔一天只看一行 Me，复述它能证明与不能证明的事情。

主读 examples/datachannel_chat.rs:113–174，对照 examples/static/chat.html:138–179。应用字段定义看 examples/datachannel_chat.rs:24–28、74–90。先读这两个小文件，不必去读整个 SCTP 栈。

协议只补充 RFC 8831 §1、§5、§6.6。消息格式、名字登记和转发规则来自本例源码，不是 RFC 规定所有聊天应用都必须使用这些 JSON 字段。
