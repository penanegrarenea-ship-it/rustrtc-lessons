sip() 加上 Keying::Dtls：给 SIP 风格对端做 DTLS-SRTP 协商（UDP/TLS/RTP/SAVPF 与 a=fingerprint）

第21课的默认 sip() 是 Sdp × None：协议 RTP/AVP，没有 ICE 属性，也没有 a=crypto。第22课只改 keying = Keying::Sdes：协议变成 RTP/SAVP，有媒体级 a=crypto，选路仍是 Sdp。第23课是 README 配方3：再同时设 Connectivity::IceLite 与 Keying::Sdes。README Configuration 表在固定提交上只有这四行（浏览器/SFU 用 webrtc()，加上三条 SIP 配方），里面没有 sip()+Keying::Dtls。本课只教这个文档允许、表内未列出的组合：从 sip() 起步，再只改 keying = Keying::Dtls，选路仍是 Connectivity::Sdp。不要把它写成配方4，不要把它写成 webrtc()，不重讲第21–23课正文，不开始下一课。

1. 为什么在 21–23 的 SIP 配方之后还要讲 Keying::Dtls

README 配方表（241–246行）只有四行：

对端起步再改什么
Browser / SFUwebrtc()（第9课起的 WebRTC 路径，Ice × Dtls × 扩展）
SIP trunk, plain RTPsip()第21课，保持 Keying::None
SIP trunk, SDES-SRTPsip()第22课，keying = Keying::Sdes
SIP phone with ICEsip()第23课，IceLite + Sdes

三条 SIP 配方都不含 Keying::Dtls。但 Keying 的文档写明：任意值可以配任意 Connectivity；数据通道需要 Dtls（config.rs 167–178行）。README 同一段也写了：“Any keying works with any connectivity; data channels need Keying::Dtls”（第250行）。所以从 sip() 只改 keying = Keying::Dtls，选路仍是 Sdp，是文档允许的组合，不是表里多出来的第五行，更不要给它起名「配方4」。

sip() 的文档注释只写了 Change keying for SDES-SRTP，connectivity for ICE-lite，没有点名 Dtls：

    /// For a SIP peer (a trunk, a phone, a PBX): the address of its SDP (no
    /// ICE), plain RTP, no WebRTC header extensions, RTCP multiplexing when
    /// the peer accepts it, a transport for each kind of media without
    /// BUNDLE. Change `keying` for SDES-SRTP, `connectivity` for ICE-lite.
    pub fn sip() -> Self {
        Self::new(
            Connectivity::Sdp,
            Keying::None,
            false,
            RtcpMuxPolicy::Negotiate,
            BundlePolicy::Balanced,
        )
    }

摘自 config.rs 977–989行 @ f1b59bf。注释没有列出 Dtls，并不表示这个组合被禁止；它只是没有被写进配方表。也不要把本课和 webrtc() 混在一起：那是全量 Connectivity::Ice、Keying::Dtls，并且打开 WebRTC 扩展、强制 RTCP mux 与 MaxBundle。

2. API 与 SDP 改了什么

Keying::Dtls 的文档是：DTLS-SRTP、a=fingerprint（RFC 5763/5764）、UDP/TLS/RTP/SAVPF（176–177行）。两种等价写法，都只改密钥交换，不改选路：

let mut config = RtcConfiguration::sip();
config.keying = Keying::Dtls;
let config = RtcConfigurationBuilder::sip()
    .keying(Keying::Dtls)
    .build();

Builder 的 RtcConfigurationBuilder::sip() 在 1127–1132行，.keying(...) 在 1222–1225行。扩展开关、rtcp_mux_policy、bundle_policy 和 connectivity 都不因这一步而改，仍是 sip() 的预设：扩展关掉、Negotiate、Balanced、Connectivity::Sdp。

build_description 里，Dtls 分支对协议不作赋值，于是保留 MediaSection::new 的默认值 UDP/TLS/RTP/SAVPF（peer_connection.rs 5748–5758行，sdp.rs 839–848行）。注释写的是 Plain-SIP profiles，WebRTC keeps the default。a=fingerprint 与 a=setup 的门闩是 self.config.keying == Keying::Dtls（6274–6292行）：Offer 的 setup 为 actpass，answer 按 dtls_role 写成 active 或 passive。同一段上面的注释写着 “Only WebRTC uses DTLS-SRTP (a=fingerprint / a=setup)”，那是在对比 SDES 不得广告 DTLS 属性；不要误读成「只有 webrtc() 才写指纹」。本轮从 sip() 起步的诊断已经写出了这两行。

4. 答案怎样带上 fingerprint 与 setup

DTLS-SRTP 不在 SDP 里放媒体密钥。RFC 5763 §5 规定：两端在 DTLS 握手里出示证书，并用 SDP 里的指纹绑定这份证书；握手出示的证书必须与指纹相符，否则必须拆掉媒体会话。RFC 5764 §3、§4.1、§4.2 再说明：SRTP 密钥是在媒体路径上用 use_srtp 从 DTLS 导出的。所以 a=fingerprint 是证书的单向散列，不是密钥，也不能用来导出媒体密钥。

RFC 8122 §5 规定指纹的写法：散列算法名，后跟冒号分隔的大写十六进制字节。本库写成 a=fingerprint:sha-256 …，由 add_dtls_attributes（sdp.rs 1341–1348行）写入媒体级。本轮诊断真实跑出的指纹是 sha-256 95:F3:F8:4E:54:E6:8F:1C:35:A8:9B:B3:0A:E2:86:64:B2:90:74:4A:B9:04:26:6B:D7:DF:18:8C:AB:52:96:66。同一进程里两个 PeerConnection 调用的 generate_certificate 会缓存并复用同一张证书（dtls/mod.rs 74–83行），所以本轮 offer 与 answer 的指纹相同。答案写的是本端证书指纹，不是从 offer 抄来的，也不等于两台机器会共用证书。

a=setup 表示谁发起这条面向连接的会话，这里就是谁先发 DTLS ClientHello。它不是 ICE 角色。RFC 4145 §4 定义 active / passive / actpass；§4.1 规定：offer 若为 actpass，answer 可以取 active 或 passive。本库的 offer 固定写 actpass；answer 按已经决定的 dtls_role 来写。本轮诊断里，对端 offer 是 actpass，本端答案写的是 a=setup:passive。

5. 容易误判的边界

  • 不要写成配方4，也不要写成 webrtc()。README 表在 pin 上只有四行。本课是文档允许的 sip()+Sdp+Dtls 组合，不是表内第五行，也不是 webrtc() 那套 Ice × Dtls × 扩展。
  • 不要把 “Only WebRTC uses DTLS-SRTP” 读成 sip()+Dtls 不写指纹。那段注释是在说 SDES 不得广告 DTLS 属性。实际门闩是 keying == Keying::Dtls。本轮从 sip() 起步的诊断已经写出 a=fingerprint 与 a=setup。
  • 指纹不是密钥，setup 不是 ICE 角色。指纹是证书散列，供对端核对手里的证书。私钥、SDES inline 密钥和 ice-pwd 真值不得出现在公开材料。完整未脱敏 SDP 也不进公开包。
  • 官方测试的起点不是 sip()。sdp_dtls 的 config() 从 webrtc() 覆盖字段。课文要教的 API 是从 sip() 只改 keying；那份 SDP 形状来自标明来源的诊断程序，不是官方测试 stdout。
  • 不要与 IceLite/Sdes 混。本课选路仍是 Sdp，密钥是 Dtls，不应再写出 a=ice-lite / a=crypto。选路对照 ice_lite_dtls、ice_dtls 若你跑了，也只说明选路不同，不是本课主路径。
  • 测试通过不等于已经从话机收到媒体。sdp_dtls 是两个本地 PeerConnection 在回环上互发媒体，不是话机，不是公网。Connected 同样不是话机收包证据。
  • 不要宣称九格都跑过。库称任意 Connectivity 可配任意 Keying；那是库的声明。本课跑了主路径 sdp_dtls、对照 sdp_none / sdp_sdes，以及可选的两条选路对照。
  • 没有官方示例文件。不要把第21课的 rtp_track_event 或官方测试改成 sip()+Dtls 再当成官方示例。不要为了让某条路径变绿去改上游。
  • 不讲 SIP 信令，不做生产 UA。把 SDP 放进 INVITE / 200 OK 是应用和信令栈的事。指纹仍需要完整的 SDP 完整性保护，见 RFC 5763 §5。

a=fingerprint 是密钥吗？a=setup 是 ICE 角色吗？本库的 offer 和 answer 分别怎样写 setup？

显示第5题答案

指纹是证书的单向散列，写在SDP里供对端核对握手证书，它并不是密钥，也不能用来导出媒体密钥。a=setup表示谁发起DTLS：本库offer写actpass，本轮诊断的answer为passive，由本端dtls_role决定。不要把setup写成ICE角色。

第6题

为什么可以展示本轮真实指纹，却不能把 DTLS 私钥、a=crypto 密钥或 ice-pwd 写进公开课文？

显示第6题答案

指纹是SDP里的公开材料，本课可以展示本轮真实跑出的值，但不得编造。对端用它核对手里的证书，不能把它当成可导出媒体的密钥。DTLS私钥、a=crypto的inline密钥、ice-pwd真值和完整未脱敏SDP，都不得出现在课文或公开包。分享前都须删掉这些秘密。

第7题

本课是不是 README 的配方4？是不是 webrtc()？源码注释 “Only WebRTC uses DTLS-SRTP” 是不是说 sip()+Dtls 不会写指纹？

显示第7题答案

不要把本课写成README配方表的配方4，那张表只有四行。也不要把它写成webrtc()那套Ice加Dtls加扩展。源码注释虽写Only WebRTC uses DTLS-SRTP，实际门闩是keying等于Dtls；本轮诊断已证实也会写指纹和a=setup。

第8题

sdp_dtls 或诊断程序通过，是不是已经从话机收到了 SRTP？官方测试是从 sip() 起步的吗？

显示第8题答案

官方sdp_dtls是两个本地PeerConnection在回环上协商并互发媒体，配置从webrtc()覆盖字段，不是从sip()起步，也不是话机或公网。诊断才从sip()起步。测试通过或Connected，不等于已经从话机收到SRTP。也未宣称九格都已跑过。
