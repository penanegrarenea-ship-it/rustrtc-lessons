DTLS-SRTP：证书、指纹与密钥

本节保存已讲过的证书核对与密钥交换流程。以下是典型 DTLS 1.2 + ECDHE、双方证书认证的完整握手概念图，不是真实抓包，不涵盖所有 TLS/DTLS 版本或算法。 不需要 clone 或运行代码。

1. 指纹来自本端证书，私钥不发送

每端先准备自己的证书和对应私钥。证书可以由端点生成，也可以预先配置，包含公钥；指纹不是另发的一把密钥：

A：证书 A + 证书私钥 A（留在本端）
   SHA-256(完整证书 A 的 DER 字节) = 指纹 A

B：证书 B + 证书私钥 B（留在本端）
   SHA-256(完整证书 B 的 DER 字节) = 指纹 B

本例把各自指纹放进 SDP，由应用信令传给对方。这里只给占位文字，不伪造可用指纹或密钥：

A 的 offer：
a=fingerprint:sha-256 <指纹A，省略的占位文字，不是合法值>
a=setup:actpass

B 的 answer：
a=fingerprint:sha-256 <指纹B，省略的占位文字，不是合法值>
a=setup:active

B 选 active，所以 B 是 DTLS 客户端，先发 ClientHello；浏览器 A 在本例是 DTLS 服务器。这个 setup 角色与谁是浏览器、谁控制 ICE、谁发送音频不是同一个概念。

依据：RFC 8122 §5、§6.2、RFC 5763 §5。

2. 信令给预期指纹，握手给实际证书

图的文字版
浏览器 A（DTLS server）                         服务器 B（DTLS client）
       │──经信令：offer 指纹A、actpass──────────────→│
       │←─经信令：answer 指纹B、active──────────────│
       │          ICE 检查并选通媒体路径             │
       │←────────DTLS ClientHello + use_srtp────────│
       │──证书A、签名认证的临时公钥Aₑ──────────────→│
       │                       B 对比证书A哈希与offer指纹A
       │←─证书B、临时公钥Bₑ、握手持钥证明──────────│
A 对比证书B哈希与answer指纹B                       │
       │     验证签名、Finished，完成其余握手检查     │
       │             导出密钥，使用 SRTP             │

图中省略了部分消息。DTLS 发生在 A、B 的媒体路径上，不是与公共 STUN 服务器握手。选中 TURN 中继路径时，TURN 仍只是转发，这次 DTLS 的两端仍是 A、B。

以 A 校验 B 为例：从 B 的 answer 保存预期指纹；从 DTLS 握手取出 B 的实际证书，计算 SHA-256，与这个远端指纹比较。B 也反过来核对 A。不是拿 B 的证书去比 A 自己 offer 的指纹。

不匹配就终止这次安全媒体连接。匹配只说明证书与 SDP 声明一致，还须通过握手签名、Finished 等检查。握手中的持钥证明用来验证对方持有证书对应私钥，不是拿一张公开证书就能冒充。

依据：RFC 5763 §5、§6.7.1、RFC 8422 §2.1、§5.8。

3. 证书认证与临时密钥交换，是两组材料

证书密钥负责握手签名与验证。临时密钥负责 ECDHE 密钥交换；两种私钥都留在本端，不发送。

A 保存临时私钥 a，发送临时公钥 Aₑ
B 保存临时私钥 b，发送临时公钥 Bₑ

A：ECDH(a, Bₑ) → 共享秘密 S
B：ECDH(b, Aₑ) → 同一个共享秘密 S

旁观者看得到证书和临时公钥，但在算法及密钥安全的前提下，不能只靠这些公开材料实际计算出共享秘密。不是“收到一把加密的共享密钥，再用私钥解密”：本例没有直接传送共享秘密，缺少的是参与计算所需的临时私钥。

证书公钥也不能直接算出 SRTP 密钥。签名认证密钥交换内容，密钥交换产生共享秘密；还要继续派生。

依据：RFC 8422 §2、§5.10。

4. 共享秘密不直接当作音频密钥

图的文字版
A：临时私钥a + B临时公钥Bₑ       B：临时私钥b + A临时公钥Aₑ
                ╲                         ╱
                 同一个 ECDH 共享秘密 S
                            ↓
        作为 premaster secret，结合握手上下文派生 master_secret
                            ↓
        exporter，标签 EXTRACTOR-dtls_srtp
                  ╱                       ╲
 client_write_SRTP_master_key/salt    server_write_SRTP_master_key/salt
    本例 B发送 ↔ A接收                   本例 A发送 ↔ B接收
                  ↓                       ↓
           SRTP 密钥派生              SRTP 密钥派生
                  ↓                       ↓
           B→A 的会话密钥             A→B 的会话密钥

这里的 client/server 指 DTLS 角色，不是 offerer/answerer 的固定别名。A 的发送密钥对应 B 的接收密钥；B 的发送密钥对应 A 的接收密钥。两个方向的主密钥材料分别派生，不是整通电话共用同一把发送钥匙。

本图的 master_secret 步骤限定 DTLS 1.2 的讲解；具体派生取决于协议版本、协商算法及扩展，不把某个公式泛化到所有 TLS/DTLS。Exporter 导出的是 SRTP 主密钥和主盐，再按选定 SRTP profile 派生实际会话密钥，不是直接把 S 拿来加密音频。

这些秘密材料由双方各自计算，不把 SRTP 密钥直接发到网络上。握手成功后，正常音频由 SRTP 保护，不是把每个音频包装进 DTLS 应用数据。常见配置使用 AES 等对称算法加密，并配合报文鉴别提供完整性保护；具体保护能力由 profile 决定，本节不展开其他 profile。

已经协商使用 DTLS-SRTP 时，握手失败不能擅自降级成明文 RTP 继续发送。

依据：RFC 5246 §8.1、RFC 5764 §4.1、§4.2、§5.1、RFC 3711 §4.3。

5. 指纹匹配的前提是信令可信

SDP 指纹需要真实性与完整性保护。若攻击者既能替换信令指纹，又能在媒体路径上冒充对端，他可以拿自己的证书匹配自己替换的指纹。单靠“匹配成功”不能保证对方身份可信，更不能单独证明对方就是某家官方服务器。

依据：RFC 5763 §8。

  2. 证书密钥与临时密钥各负责什么？A 用哪两项算共享秘密？

  4. 本例 B 是 DTLS client，client_write 的材料用于哪个方向？握手后正常音频走 DTLS 应用数据还是 SRTP？
  5. 信令指纹和媒体证书一起被攻击者替换，仅靠指纹匹配足以证明身份吗？
作答后查看参考答案

1. B 的 answer 指纹；不匹配就终止。2. 认证握手、产生共享秘密；A 临时私钥加 B 临时公钥。3. 都不是，还需密钥派生。4. B→A；SRTP。5. 不足以，信令真实性与完整性也是前提。
