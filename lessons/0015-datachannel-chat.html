先跑一个能互发消息的小程序，再把上一课的“描述、路径、安全、应用结果”落实到证据。目标不是一口气写完整 WebRTC 栈，而是：用两个浏览器页面，经 Rust 服务端双向聊天，并能指出 HTTP 在哪里结束、DataChannel 在哪里接手。

建议 30–40 分钟：运行与验收 10–15 分钟，读核心代码 12 分钟，排错与练习 8–13 分钟。首次下载、编译可能另需时间。你已熟悉 Rust async/tokio，本课不讲语言基础或环境安装。0014 尚未提交答案，不假定已经掌握；本课会带着你复用证据分层。

本课钉住 rustrtc 0.6.4 的完整提交 f1b59bf6e85fa529dc0c8ed94a91e17a00cd8afa。所有下方源码永久链接均指向这个 SHA，并注明文件与行号。旧课引用的 e13b5f2 不变，不能混用别的 checkout 的行号。

验证边界：课前已在云端 Linux、rustc 1.100.0、真实 Chrome 的两个页面中连续两次跑通，未改示例。不是在你的 Windows，也不是在教学共享电脑上复跑；下方 Windows 命令供你实操，未声称已在 Windows 验证。成功截图采集超时，因此本课用实际日志和页面文字，不展示伪造或较早未连通的截图。

2. 两个页面，明确的验收目标

在同一台电脑打开两个页面，按这个顺序做：

  1. 第一个页面输入名字 Alice，点击 Connect。等 Status: Connected 和 Connected as Alice，Send 变为可用。
  2. 第二个页面输入不同名字 Bob，点击 Connect，同样等 Connected。
  3. Alice 输入 hello-from-alice，点击 Send。必须在 Bob 页面看见 Alice: hello-from-alice。
  4. Bob 输入 hello-from-bob，点击 Send。必须在 Alice 页面看见 Bob: hello-from-bob。
  5. 记下两边是否 Connected、对方是否收到消息、终端是否记录通道打开。不要公开真实 SDP、ICE 密码或私人聊天内容。

按钮实际叫 Connect / Send / Disconnect，没有 Join 按钮。界面初始 Send 与 Disconnect 不可用；通道打开后才启用。依据：examples/static/chat.html:44–46、137–178。

只在本页看到 Me: ... 不算发送到对端的证据。页面是在调用发送后自行追加这行文字，不是等待服务端回执。验收必须看另一页收到的内容。examples/static/chat.html:171–178

这不是 Alice 浏览器直连 Bob 浏览器。每个页面各连 Rust 服务端，服务端把消息广播给其他客户端；不是音频回声，也不访问麦克风。

3. 第一张图：一次 HTTP 协商，之后走数据通道

图 1 是依据示例代码画出的流程示意，不是抓包或实测时序。两个页面各自执行一次这样的连接流程。

浏览器先创建连接和通道，再生成 offer、设置本地描述，等待 ICE gathering complete，最后发送一次 POST。下面两段是原文件的分段摘录，中间省略了打印候选和等待收集完成的代码；不要把两段直接拼成跳过等待的新实现。

pc = new RTCPeerConnection();

// Use negotiated data channel (ID=0) to match server behavior
dc = pc.createDataChannel("chat", { negotiated: true, id: 0 });
setupDataChannel(dc, name);

摘自 examples/static/chat.html:79–85。

const response = await fetch('/offer', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ sdp: pc.localDescription.sdp })
});

const answer = await response.json();
await pc.setRemoteDescription(new RTCSessionDescription({ type: 'answer', sdp: answer.sdp }));

摘自 examples/static/chat.html:109–116。请求 JSON 只有 sdp，不是你凭印象补出来的 {type, sdp}；响应含 answer 类型，页面这里显式使用 type: 'answer'。

等待逻辑在 examples/static/chat.html:91–107。onicecandidate 这里只打印候选，没有逐条发送新候选的请求；服务端路由也没有 /candidate。examples/static/chat.html:85–89、examples/datachannel_chat.rs:46–55

所以这是完整收集后交换 SDP，非 Trickle ICE。一次连接的一次 POST，不等于以后重连也永远只有一次；更不表示生产系统必须这样设计。HTTP 200 仅说明这次应用请求得到响应，不等于 ICE 或 DataChannel 已成功。

4. Rust 端：双方预先约定 chat / id 0

服务端每收到一个 offer，就解析描述、选用 WebRTC 配置、建立自己的连接。下面是原文相邻摘录，没有把 unwrap() 改成另一种错误处理，也不是生产级输入验证范例。

let offer_sdp = SessionDescription::parse(SdpType::Offer, &payload.sdp).unwrap();
let config = RtcConfiguration::webrtc();
let pc = PeerConnection::new(config);

// Use negotiated data channel with ID 0
let dc = pc
    .create_data_channel(
        "chat",
        Some(rustrtc::transports::sctp::DataChannelConfig {
            negotiated: Some(0),
            ..Default::default()
        }),
    )
    .unwrap();

调用位置（包含本段所有 rustrtc 类型/函数）：examples/datachannel_chat.rs:94–109。配置入口另见 RtcConfiguration::webrtc，src/config.rs:967–975；通道创建签名见 PeerConnection::create_data_channel，src/peer_connection.rs:4119–4186。

对照两端，不要把 Rust 的 Some(0) 误读为 JavaScript 布尔值 false：

  • 浏览器：negotiated: true, id: 0。
  • Rust：DataChannelConfig { negotiated: Some(0), ..Default::default() }。这里的 Option 同时表达“已在应用层约定”及通道编号 0；字段与内部转换见 src/transports/datachannel.rs:147–161、189–199。
  • 双方都使用 label chat，并明确约定 id 0。只把名字写成一样，不是所有场景下自动匹配的协议。

本例不靠 DCEP OPEN/ACK 协商通道。源码在非 negotiated 时才进入发送 DCEP OPEN 的分支：src/peer_connection.rs:4169–4184。已经约定通道参数，不表示可以省去 ICE、DTLS 或 SCTP 建立。

作为对照，DCEP 是另一种带内建通道的方法：发送 OPEN，对端 ACK。参见 RFC 8831 §6.5、RFC 8832 §4、§5.1、§5.2。这是对照知识，不是声称本次聊天抓到了 OPEN/ACK。

5. Rust 端：等候选收集完成，再发 answer

下面是原示例的连续摘录。留意它实际调用了两次创建 answer，第一份返回值没有作为 HTTP 响应发出；不要悄悄删掉一行再声称是原文。

pc.set_remote_description(offer_sdp).await.unwrap();
let _ = pc.create_answer().await.unwrap();
pc.wait_for_gathering_complete().await;
let answer = pc.create_answer().await.unwrap();
pc.set_local_description(answer.clone()).unwrap();

Json(OfferResponse {
    sdp: answer.to_sdp_string(),
    type_: "answer".to_string(),
})

调用位置（含上述描述解析结果、描述设置与生成函数）：examples/datachannel_chat.rs:206–215。wait_for_gathering_complete，src/peer_connection.rs:4270–4287 等待收集状态到 Complete，不是等待 ICE 检查已经选路、DTLS 已完成、对端已经收消息。

读代码时用三种不同问题做标记：

  1. set_remote_description：程序拿到了哪份远端描述？
  2. gathering complete：程序是否已把本轮候选收集完？
  3. DataChannel open、对页收消息：运行是否推进到可交换应用数据？

这些调用在本例中的位置均见上面的 206–215 行；不能把“已有 answer”写成“通道已经 open”。本课只解释当前示例，不把这段结构宣称为所有连接场景的唯一最佳写法。

6. 打开后再登录、发送、接收与转发

页面的通道打开回调会启用输入和按钮，并立即发送 login。以下原文摘录属于应用层聊天协议，不是 ICE 密码认证，也不是 DCEP OPEN。

channel.onopen = () => {
    statusDiv.textContent = "Status: Connected";
    msgInput.disabled = false;
    sendBtn.disabled = false;
    disconnectBtn.disabled = false;
    log("Connected as " + name, "info");

    // Send login message
    channel.send(JSON.stringify({ type: "login", name: name }));
};

来源：examples/static/chat.html:137–147。发送按钮还会检查 dc.readyState === 'open'，然后发送 {type: "chat", content: ...}。examples/static/chat.html:171–178

图 2 是代码职责示意，不是实测消息延迟图：

Rust 发送侧使用 PeerConnection::send_text，src/peer_connection.rs:4201–4210，第一个参数是 channel id。本例转发调用是 send_text(0, msg.text)，位置见 examples/datachannel_chat.rs:122–131。

不要把页面的 readyState 门禁归给 Rust API：这个 send_text 实现检查 SCTP transport 是否存在，没有在这里检查通道的 Open 状态；不存在时返回 InvalidState("SCTP not connected")。因此应用仍应遵守通道就绪条件，不能推断“调用 API 就替我保证对端收到”。这是固定源码的行为边界，不是本课新复现了失败分支。

7. 第三张图：聊天不是 SRTP 音频

图 3 是协议分层示意。为看清区别省略包头和复用细节，不是实际报文布局。

DataChannel 在 DTLS 里承载 SCTP 数据；不能把它说成“聊天文字装进音频 SRTP”。音频使用 SRTP 的密钥建立可与 DTLS 有关联，但音频媒体并不是因此变成普通 DTLS 应用数据。依据：RFC 8831 §1、§5、§6.6。

本例的 open 不证明音频可播放。它没有验证麦克风、音频 PT/编码、SRTP 媒体接收、解码器或扬声器；也没有示范 SIP 信令。上课的证据分层仍然成立，但这次应用结果是“另一页收到聊天消息”，不是“听到声音”。

本地 HTTP 信令演示也不是可直接部署的安全模型。不要把监听地址改成公网就当生产服务，不要使用真实私人内容来做公开演示。

同轮实际页面文字摘录：

  • Alice：Connected as Alice；[System]: Bob joined the chat；Me: hello-from-alice；Bob: hello-from-bob。
  • Bob：Connected as Bob；Alice: hello-from-alice；Me: hello-from-bob。

各项结果要分开解释：HTTP 200 证明应用响应；gathering complete 证明候选收集结束；ICE connected 支持路径连通状态；open 支持数据通道打开；对页出现相应内容才支持本次应用数据传达。没有单项能证明未来永不掉线。

另一个边界容易忽略：http://127.0.0.1:3000/ 是 HTTP 入口，不自动说明 ICE 也使用环回地址。此轮成功连接实际使用非环回 host 候选，没有 srflx 或 relay；不公开具体候选地址。WebRTC 配置默认 ICE 服务器列表为空，且默认不包含环回候选：src/config.rs:998–999、1038–1039，相关地址筛选见 src/transports/ice/mod.rs:5239–5265。

所以只能说“这次本地双页面互通成功”。没有验证跨公网，没有配置 STUN/TURN，也没有复现只有环回网卡的机器会怎样失败。不能把这些未测条件写成通过或必然失败。

9. 三个排错场景：从最后一条可靠证据向后查

场景 A：服务没起来，或者只有根页面能开

若终端提示地址已占用，先确认是否自己另一个示例还在运行。这份示例绑定 127.0.0.1:3000，不能假设命令带了可改端口参数。只停止自己确认的旧服务，不去结束不认识的进程。examples/datachannel_chat.rs:46–55

若 / 能开，/static/chat.html 却 404，核对启动工作目录。根页面经编译时嵌入，静态目录按运行时相对路径 examples/static 查找：examples/datachannel_chat.rs:46–60。云端实际验证了错误工作目录下 200/404、仓库根目录下 200/200。favicon.ico 404 单独出现不等于聊天失败。

场景 B：POST /offer 为 200，但 Send 还不能用

这不是“HTTP 已成功所以一定是按钮坏了”。检查浏览器是否真的收到并设置 answer、候选是否收集并交换、当前 ICE 状态是否推进、DTLS/SCTP 与通道是否打开；按最后已确认的一层向后查。具体缺证据时，写“尚未证实 open”，不要自动判定某层故障。

默认未配 STUN/TURN，跨网络不能照搬本机成功。本节不编造配置补丁，不让你关掉证书验证、明文替代 DTLS 或随便改通道 id 来碰运气。先保留脱敏状态和错误；不要把完整凭证贴到公开仓库。

场景 C：本页已有 Me，另一页没看到

先分别核对两页是否 open、用了不同用户名、是否在 open 之后完成应用 login、发送内容非空，以及服务端是否收到并转发。最后看对端是否处理并显示消息。只看本页的 Me 不足以定位断点。

应用登录、聊天广播、接收显示的依据仍是 examples/datachannel_chat.rs:117–174 与 examples/static/chat.html:137–178。这些是排查路径，不是声称三个故障都已在课前复现。

10. 小实践：不改协议，改变消息并证明到达

先完成原样双向验收，再做一个能立即核对的小变化：无需修改 Rust API、SDP 或通道编号。

  1. 保持 Alice / Bob 两页已连接。Alice 发 lesson-0015-check-1，Bob 回 received-check-1。
  2. 分别记录“发送页本地 Me”和“接收页对方名字”两项，比较哪项能证明对页收到。不要只交一张发送侧文字。
  3. Bob 点击 Disconnect；待界面恢复可连接后，把用户名改成 Bob2，再点击 Connect。等连接完成后重新互发一条带新标记的消息，观察 Alice 的接收署名。
  4. 写一张四行卡：固定 SHA；HTTP 与数据通道的分界；双方实际应用接收证据；尚未验证的条件（例如跨公网和音频）。

前两步复用课前已验证的发送路径。第三步是给你的实操观察任务：页面确有断开/重新启用名字输入的处理，但本课云端记录没有单独验收 Bob2 重连，不把练习目标写成已经观察到的结果。相关界面处理见 examples/static/chat.html:119–135、160–167。

11. 八道自测

先独立答，最后展开参考答案；不必逐题等聊天回复。简答题没有靠选项长度暗示答案。

  1. 为什么要在 Bob 页面看到 Alice: hello-from-alice，不能只凭 Alice 的 Me: hello-from-alice 验收成功？
  2. 本例每个页面连接时，POST /offer 的请求 JSON 有哪些字段？候选是逐条经额外请求发送的吗？HTTP 200 能否证明 open？
  3. 浏览器 negotiated: true, id: 0 对应 Rust 的哪项值？本次是否发送 DCEP OPEN/ACK 来协商 chat？哪些底层建立仍不可省略？
  4. 服务端等待 gathering complete，与等到 DataChannel open 是同一件事吗？代码实际把第几份创建出的 answer 发回？

参考答案

第 1 题参考答案

Me 是发送页面自行追加的文字，不是服务端或对端回执。另一页显示带发送者名字和对应标记的消息，才支持该次应用消息传达。

第 2 题参考答案

请求只有 sdp；页面等待候选收集 complete 后一次发送，onicecandidate 只打印，不是 Trickle。HTTP 200 不证明通道 open。

第 3 题参考答案

对应 DataChannelConfig.negotiated 的 Some(0)，双方已约定 chat/id0，不靠 DCEP OPEN/ACK 建通道。ICE、DTLS、SCTP 仍需建立。

第 4 题参考答案

不同：前者是候选收集结束，后者是数据通道已打开。原代码第一份 answer 返回值丢弃，等待后生成并发回第二份。

第 5 题参考答案

login 是应用聊天协议，不是安全身份认证或 DCEP。聊天 JSON 走浏览器到 Rust 的数据通道，再由 Rust 广播给其他客户端，不是逐句 POST 或浏览器直连。

第 6 题参考答案

0 是通道编号。Rust 此实现检查 SCTP transport 是否存在，不检查浏览器 readyState/Open；页面自己有 open 门禁。调用发送不保证对页已接收或显示。

第 7 题参考答案

先核对是否从仓库根目录启动：根 HTML 编译时嵌入，静态目录是相对路径。HTTP 入口与 ICE socket 路径不同；此轮实际用非环回 host 候选，默认不含环回候选。

第 8 题参考答案

云端双页面确有对方消息支持本次本地应用互通；无 STUN/TURN 的测试不证明跨公网。DataChannel 的 SCTP/DTLS 路线不等于音频 SRTP、解码与播放验证，open 也不证明扬声器有声。
