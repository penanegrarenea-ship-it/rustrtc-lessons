2. 每个进入建连段的 offer 创建自己的连接对象

路由把 POST /offer 交给示例自己的 offer 函数，见 examples/datachannel_chat.rs:46–50。函数名不是rustrtc替你提供的HTTP信令服务。请求和响应的应用结构体如下：

#[derive(Deserialize)]
struct OfferRequest {
    sdp: String,
}

#[derive(Serialize)]
struct OfferResponse {
    sdp: String,
    #[serde(rename = "type")]
    type_: String,
}

来源：examples/datachannel_chat.rs:62–72。请求只有sdp字符串。响应有sdp和序列化后叫type的字段。OfferRequest、OfferResponse 是示例定义，不是聊天消息，也不是ICE或DTLS报文。

handler开头是连续原文：

async fn offer(
    State(state): State<AppState>,
    Json(payload): Json<OfferRequest>,
) -> impl IntoResponse {
    let offer_sdp = SessionDescription::parse(SdpType::Offer, &payload.sdp).unwrap();
    let config = RtcConfiguration::webrtc();
    let pc = PeerConnection::new(config);

    // Use negotiated data channel with ID 0
    let dc = pc
        .create_data_channel(
            "chat",
            Some(rustrtc::transports::sctp::DataChannelConfig {
                negotiated: Some(0),
                ..Default::default()
            }),
        )
        .unwrap();
    let dc_clone = dc.clone();
    let pc_clone = pc.clone();

来源：examples/datachannel_chat.rs:92–111。这段包括下列API和类型的真实调用位置：SessionDescription::parse、SdpType::Offer、RtcConfiguration::webrtc、PeerConnection::new、create_data_channel、DataChannelConfig。没有把原来的unwrap改成问号，也不是可以直接部署的错误处理范例。

按对象而不是按变量名猜职责：

  • payload.sdp 是浏览器送来的文本。parse把它解释为远端Offer描述。解析成功不证明里面的候选地址可达。
  • config 是本次创建连接所选的配置。此处明确调用webrtc，不是把浏览器offer当成本端配置。该配置的WebRTC机制说明见 src/config.rs:967–975。
  • pc 是Rust端这次连接的对象。创建它不等于拿到了“已连通”的证据。
  • dc 是本次连接中创建的通道句柄。这里得到句柄，还不能当成已经观察到Open事件。

3. 先约定通道，再设置远端 offer

在本例中，创建通道位于设置远端描述之前。Rust通道配置是 negotiated: Some(0)，调用位置已在 examples/datachannel_chat.rs:100–109。浏览器对应原文是：

pc = new RTCPeerConnection();

// Use negotiated data channel (ID=0) to match server behavior
dc = pc.createDataChannel("chat", { negotiated: true, id: 0 });
setupDataChannel(dc, name);

来源：examples/static/chat.html:79–83。两端事先约定同一个通道编号0。negotiated 不是“自动跳过底层建连”，label相同也不等于对端必然知道所有参数。

本例不靠DCEP的OPEN和ACK创建这个通道。固定实现中的非negotiated分支才发送OPEN，见 src/peer_connection.rs:4169–4184。带外约定仍需要双方一致，依据 RFC8831 §6.5。DCEP的带内握手作为对照，见 RFC8832 §4。不把这个对照画成本例真实发出的报文。

之后handler调用 set_remote_description(offer_sdp)，见 examples/datachannel_chat.rs:206–206。这里的remote是Rust端的远端，也就是浏览器。末尾设置local时则是Rust自己生成的answer。不要把remote/local永远等同于offer/answer：那只是本例Rust作为应答端时的对应。

这次配置、创建通道、准备接收任务、设置远端描述的前后顺序，来自这个固定示例。不要据此宣称所有rustrtc应用、所有协商阶段都必须照这一个模板排列，也不要本课自行删改顺序测试。

4. 两次创建 answer，不是两轮协商

回到开篇的 examples/datachannel_chat.rs:206–215，按实际执行顺序编号：

  1. 设置浏览器的远端offer。
  2. 调用第一次create_answer，丢弃它的返回值。
  3. 调用wait_for_gathering_complete并等待。
  4. 调用第二次create_answer，把它绑定到answer。
  5. 将answer的clone设为Rust本地描述。
  6. 将同一个answer序列化进HTTP响应。

最后返回的是第二份，不是第一份。源码确实有两次创建，不能为了让摘录更短就删掉一次。本课只确认可见的调用和数据流，不推测第一调用的所有内部副作用，也不把“两次”当作你未来代码的通用要求。

两次在本地产生描述，不等于浏览器与Rust已经交换了两轮offer/answer。浏览器这一次发送POST后，取得响应并设置远端answer，原文如下：

const response = await fetch('/offer', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ sdp: pc.localDescription.sdp })
});

const answer = await response.json();
await pc.setRemoteDescription(new RTCSessionDescription({ type: 'answer', sdp: answer.sdp }));

来源：examples/static/chat.html:109–116。结合前面的 examples/static/chat.html:91–107 可见，浏览器也是先等本端候选收集，再发这次POST。onicecandidate这里只打印，见 examples/static/chat.html:85–89。本例走完整收集后交换，不是每产生一个候选就额外发送一次请求。

gathering complete只回答收集问题

直接看本版本等待函数，不靠名字猜。以下是完整函数：

pub async fn wait_for_gathering_complete(&self) {
    if self.config().connectivity.is_direct() {
        // Direct transport: no ICE gathering needed. Gathering completes
        // synchronously when setup_direct_rtp_offer_with_rtcp is called.
        return;
    }
    let _ = self.inner.ice_transport.start_gathering();
    #[allow(unused_mut)]
    let mut rx = self.subscribe_ice_gathering_state();
    loop {
        if *rx.borrow_and_update() == IceGatheringState::Complete {
            return;
        }
        if rx.changed().await.is_err() {
            return;
        }
    }
}

来源：src/peer_connection.rs:4270–4287。本课webrtc配置不走上面的direct提前返回分支。对这里的ICE分支，只需读出三件事：它调用start_gathering，它观察收集状态，它在Complete或状态通知通道关闭时返回。

因此需要区分两种证据：实际观察到收集状态Complete支持本轮收集结束；只看到等待函数返回不能不看返回路径就无限扩大结论。这段函数并没有等待DataChannel的Open事件，也没有承诺对方已经收到answer。

不要把“收集完候选”写成“已经测试并选定可用路径”。候选收集、连通性检查、提名分别见 RFC8445 §2.1、§2.2、§2.3。本课不重讲优先级与NAT类型。

事件任务还监听ICE状态。以下是select中的另一个原文分支：

res = ice_state_rx.changed() => {
    if res.is_ok() {
        let state = *ice_state_rx.borrow();
        if state == rustrtc::IceConnectionState::Disconnected
            || state == rustrtc::IceConnectionState::Failed
            || state == rustrtc::IceConnectionState::Closed
        {
            info!("ICE connection ended for client {}: {:?}", my_id, state);
            break;
        }
    } else {
        break;
    }
}

6. 用证据说明“成功到哪里”

页面的Connected来自数据通道的onopen，不是HTTP响应事件。原浏览器代码如下：

    statusDiv.textContent = "Status: Connected";
    msgInput.disabled = false;
    sendBtn.disabled = false;
    disconnectBtn.disabled = false;
    log("Connected as " + name, "info");

    // Send login message
    channel.send(JSON.stringify({ type: "login", name: name }));

来源：examples/static/chat.html:138–147。它在这里启用Send并发送应用login。Connected as本身仍不是Rust登记名字的回执，详见0016消息证据。

你有的证据它支持什么单凭它不能推出什么

7. 三种分析卡：先写缺什么，别急着改程序

以下都是教学分析场景，不是声称本课刚复现的故障。

A：浏览器收集完成，POST一直没响应

先分清“浏览器自己的收集完成”和“Rust自己的收集完成”。本例Rust收到请求后还有解析、设置描述、生成answer和等待收集等步骤。仅凭请求pending，不能定位为某一个await卡住。

交出请求是否真正发出、终端实际错误、服务是否仍运行等证据。没有内部观测时就写“尚不能确定停在哪一步”。不要删除等待、重复创建连接，或者强改候选来碰运气。源码顺序见 examples/datachannel_chat.rs:92–115、examples/datachannel_chat.rs:206–215。

B：已经拿到answer，Send仍是disabled

先核对浏览器是否成功设置了远端answer，再找本页onopen证据。只拿到JSON不是回调已触发。Send在open回调里启用，依据 examples/static/chat.html:109–116、examples/static/chat.html:138–147。

后续再按现有状态和错误检查ICE、DTLS、SCTP或应用处理，不能在没有证据时断言某一层已坏。negotiated也不提供绕过这些建立条件的捷径。不要关证书检查、改成明文或随便改通道编号。

C：曾经Open，后来看到ICE connection ended

先确认同一连接编号，读实际状态值。这个示例的事件任务会在上述三个状态之一时离开循环，再走自己的清理路径。此前一次Open不证明任务现在仍在接收，也不保证刚发的新消息可达。

依据仍是 examples/datachannel_chat.rs:176–204。这只解释例源的退出条件，不是把短暂断连等同所有WebRTC应用都无法恢复。本课没有新增掉线实测，不编造恢复时间。

8. 唯一练习：一张调用顺序与事件证据卡

可以完全纸面完成，不运行新代码，也不修改示例。若0015已跑通，可以附真实观察，但不要把本课预期填成实测结果。

先给这八张纸卡排序。D中的启动任务表示spawn调用的位置，不表示任务已运行到Open：

  • A：返回包含answer的HTTP JSON。
  • B：设置浏览器offer为Rust远端描述。
  • C：解析offer，选择webrtc配置并创建Rust连接。
  • D：准备克隆句柄和广播订阅，调用spawn启动事件任务。
  • E：创建预先约定id0的chat通道。
  • F：等待候选收集。
  • G：第一次创建answer，返回值未发出。
  • H：第二次创建answer，并设置为Rust本地描述。

交同一张卡的六行即可：

  1. 固定SHA和正确纸卡顺序。
  2. 每个步骤所在的示例文件行号。
  3. 浏览器offer、Rust answer分别在哪一侧是local和remote。
  4. handler返回后哪两个任务还可能继续，依据哪些捕获值和退出条件。
  5. 从证据表任选两项，各写一条“支持什么”和“一条仍未知”。
  6. 注明“纸面推演”或“自己实际观察”。若有运行，仅附无凭证状态和本次唯一教学标记。

9. 八道自测

先一次答完，再分别展开参考答案。题目均为简答，不用选项长度提示答案。

  1. POST的sdp由谁产生？解析成offer之后，能否证明其中候选可达？config、pc、dc各是什么？
  2. 本例Rust在设置远端offer之前还是之后创建通道？Some(0)对应浏览器哪两个配置项？为什么不等于底层已经建立？
  3. 第一份和第二份answer分别去了哪里？两个create_answer调用是否就表示两轮信令协商？
  4. 等待函数的ICE分支有哪些返回条件？实际观察到gathering Complete，和通道Open分别回答什么问题？
  5. handler已返回JSON，为什么仍有代码接收通道事件？从句柄捕获与任务位置解释，不用“HTTP一直没断”解释。
  6. 同一连接观察到Disconnected时，这个示例如何结束事件循环、处理转发任务？能否说这是所有应用都必须采用的策略？
  7. 浏览器拿到answer JSON，但Send不能用。最后确认了哪一层？下一条需要的证据是什么？为何不能直接改通道id？
  8. 给出八张纸卡的顺序。再判断“Rust有Open日志，所以Bob已经收到A1，而且音频可播放”缺了哪些独立证据。

参考答案

第 1 题参考答案

浏览器生成并发送自己的本地描述。parse是描述解析，不是地址连通性测试。config选配置，pc是Rust本次连接对象，dc是它创建的通道句柄。这些创建与解析结果不替代运行证据。

第 2 题参考答案

之前。Rust的Some(0)对应浏览器negotiated为true、id为0。它们是两端预先约定通道参数，不是已完成ICE、DTLS、SCTP或已观察Open。

第 3 题参考答案

第一份返回值丢弃，第二份设为本地描述并序列化进HTTP响应。只有一次浏览器POST及相应answer响应，不能按本地函数调用次数计算信令轮数。

第 4 题参考答案

ICE分支在状态为Complete或状态通知通道关闭时返回。实际Complete支持本端收集结束；Open支持本端通道打开。它们都不单独证明另一页已经显示消息。

第 5 题参考答案

handler之前调用了spawn，事件任务捕获dc_clone、pc_clone等句柄，转发任务持有pc_sender。它们有独立的等待和退出逻辑。HTTP响应返回不等于后台任务同步结束，也不等于任务永久存活。

第 6 题参考答案

例源在观察到Disconnected、Failed或Closed时离开循环，之后abort转发任务，并在已有名字时构造left通知。这是该示例策略，不是RFC规定所有应用短暂Disconnected都要永久终止；也不承诺同步清理完或通知立刻显示。

第 7 题参考答案

只确认取得了信令响应描述，还需检查设置远端answer是否成功和本页onopen证据。不能由缺证据直接认定某层故障，随便改id可能破坏两端原本一致的约定。

第 8 题参考答案

C、E、D、B、G、F、H、A。Rust的Open不证明Bob接收并显示A1，必须找正确Bob页的本轮标记。DataChannel聊天也不验证音频SRTP、编码、解码和播放。
