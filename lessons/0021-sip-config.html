1. 为什么在 audio_saver 之后改用 sip()

第20课的对端是浏览器：完整 ICE、DTLS-SRTP、WebRTC 扩展。所以它用 RtcConfiguration::webrtc()。本课的对端是示例里那段模拟 SIP INVITE 的音频 SDP：m=audio 5004 RTP/AVP 8 101，PCMA PT 8，没有 ICE 候选，没有 a=crypto，也没有指纹。第13课的判读结论就是：选路走 SDP 地址，密钥方式是纯 RTP。对应到本库，起点应是 RtcConfiguration::sip()，不是再复制一份 webrtc()。

rustrtc 只生成和解析 SDP，并收发 RTP/SRTP。把这段 SDP 放进 SIP INVITE / 200 OK，是 rsipstack 和应用的事。本课只把 offer 当作已经到达的文本，不讲 INVITE 流程。

来源：示例注释与远程 SDP 见rtp_track_event.rs 11–54行；sip() 构造见config.rs 977–989行。第13课只做 SDP 判断，见第13课目标段。

2. webrtc() 与 sip() 差哪五个字段

没有一个叫“默认配置”的安全起点。注释写明：从对端种类起步，webrtc() 或 sip()，再改需要改的字段。二者只差这五个字段，其余字段起点相同。出处：config.rs 589–595行、964–989行，以及README Configuration 对照表。

字段webrtc()sip()
connectivityIceSdp
keyingDtlsNone
webrtc_extensionstruefalse
rtcp_mux_policyRequireNegotiate
bundle_policyMaxBundleBalanced

枚举定义在同一文件：Connectivity 是 Sdp / IceLite / Ice（145–158行），Keying 是 None（RTP/AVP）/ Sdes（a=crypto，RTP/SAVP）/ Dtls（指纹，UDP/TLS/RTP/SAVPF）（167–178行）。IceLite 对应 RFC 8445 §2.5：lite 代理只用 host 候选，不主动发起检查、不跑那些状态机，但必须能应答对端的连通性检查。Builder 等价物是 RtcConfigurationBuilder::webrtc() / ::sip()（1119–1132行），再用 .connectivity(...)、.keying(...)（1216–1225行）。

    pub fn sip() -> Self {
        Self::new(
            Connectivity::Sdp,
            Keying::None,
            false,
            RtcpMuxPolicy::Negotiate,
            BundlePolicy::Balanced,
        )
    }

摘自 config.rs 981–989行 @ f1b59bf。

README 还写：任意 Keying 可配任意 Connectivity；数据通道需要 Keying::Dtls。那是库的声明。本课只教能在 README 配方或已跑测试里对上的组合，不宣称自己跑过全部九格。

3.2 本轮官方示例实际打印了什么

示例先用 RtcConfiguration::sip() 建 PeerConnection，再添加 MediaKind::Audio、RecvOnly 的 transceiver，然后 set_remote_description 那段模拟 INVITE。随后它读取 receiver.ssrc()，并断言该值落在 2000–2999。来源：32–67行。

# 示例内嵌的模拟远程 offer，原文如此，不是一次真实 INVITE
v=0
o=- 123456 123456 IN IP4 10.0.1.100
s=SIP Call
c=IN IP4 10.0.1.100
t=0 0
m=audio 5004 RTP/AVP 8 101
a=rtpmap:8 PCMA/8000
a=rtpmap:101 telephone-event/8000
a=fmtp:101 0-15
a=sendonly
a=mid:0

本轮 stdout 在 2026-11-27 12:01:25.141747 JST（由日志中的 UTC 换算）打印了这段 offer，并写：

📊 Initial SSRC: 0 (provisional, range 2000-2999)

随后 stderr：thread 'main' panicked at examples/rtp_track_event.rs:67:9: Should be provisional SSRC，退出码 101。没有 create_answer 的输出，没有 “Example complete”，没有 Track 事件。示例在断言之后才调用 create_answer 并睡眠 2 秒（70–121行），本轮没有走到那里。调试日志里出现过本机 host 候选地址，那只是内部传输层打的 DEBUG，不能当成 SDP 里协商了 ICE；以正式 SDP 属性为准。

这与同一提交的库行为一致，不是你的环境配错。add_transceiver 用 RtpReceiverBuilder::new(kind, 0) 创建接收器，初始 SSRC 就是 0（1331–1337行）。官方测试 rtp_mode_track_event_after_set_remote（12508–12533行）和 rtp_mode_sends_track_event_after_ssrc_latching（11515–11547行）都断言：offer 没有 a=ssrc 时，receiver.ssrc() 应为 0。若 offer 带 a=ssrc:55555，rtp_mode_track_event_with_remote_ssrc（12537–12559行）则要求接收 SSRC 等于 55555。RFC 3550 §3 把 SSRC 定义为 RTP 头里的 32 位随机标识，并不是 2000–2999 这个区间。示例注释和断言仍写着旧约定，已经和本提交的库及测试不一致。本课不要改上游示例去“修绿”。

3.3 官方测试里 sip() 的 answer 长什么样

本轮在同一提交、同一工具链上跑了 11 个官方库测试，全部通过（2026-11-27 12:11:23 JST，退出码 0，测试本身约 0.03 秒）。其中与读 SDP 直接相关的是：

  • rtp_mode_no_ice_dtls_artifacts（12325–12380行）：sip() 的 offer 必须是 RTP/AVP，且不得含 ice-ufrag、ice-pwd、a=candidate、fingerprint、a=setup:。
  • rtp_mode_no_ice_lite_no_ice_attributes（13280–13313行）：未改成 IceLite 时，不得有 ice-lite / ice-ufrag / a=candidate。
  • rtp_mode_answer_omits_rtcp_mux_when_offer_omits_it（12565–12607行）：offer 没有 a=rtcp-mux 时，answer 不得广告 a=rtcp-mux，但应有单独的 a=rtcp:。这与 sip() 的 RtcpMuxPolicy::Negotiate 一致。
  • rtp_mode_answerer_connects_on_set_remote（12289–12321行）：answerer 在 set_remote_description 之后可以把连接状态推到 Connected，远程地址来自 offer 的 c=/m=。这只证明按 SDP 地址做了直连设置，不是 Track 事件，也不是收到了音频 RTP。

这些测试本身并不把完整 SDP 打印到 stdout。为了看到“同一段示例 offer、同一个 sip()、同一个 RecvOnly transceiver”在跳过过时断言之后会写出什么 answer，教学验证另写了一个不发表、不要求你运行的诊断程序：它只是复用示例的 offer 与 sip()，不改库。诊断在 2026-11-27 12:10:51–12:11:20 JST 运行，退出码 0；set_remote 与 set_local 之后 SSRC 仍是 0，2 秒内没有 Track 事件。下面是该诊断 answer 的脱敏摘录，地址和端口已替换，不能拿去部署。它不是官方示例的 stdout。

# 诊断程序的本地 answer，截取且已脱敏，不是官方示例输出
v=0
o=- [sess] [vers] IN IP4 [addr]
s=-
c=IN IP4 [addr]
t=0 0
m=audio [port] RTP/AVP 111
a=mid:0
a=recvonly
a=rtpmap:111 opus/48000/2
a=fmtp:111 minptime=10;useinbandfec=1;stereo=1
a=rtcp:[rtcp-port]

先看对上的部分。协议是 RTP/AVP，没有 a=crypto、没有 ice-ufrag/ice-pwd、没有 fingerprint，与 Keying::None、Connectivity::Sdp 一致。offer 是 a=sendonly，answer 是 a=recvonly，符合 RFC 3264 §6.1：sendonly 的 offer 对应 recvonly 或 inactive 的 answer。offer 没有 a=rtcp-mux，answer 带了 a=rtcp:，与上面那条官方测试一致。端口不是 0，按同一节，端口为 0 才表示拒绝该流。

再看需要对上 offer 的部分。默认 media_capabilities 为 None 时，用内置集合：音频是 Opus + PCMU，不是 PCMA（MediaCapabilities::default 519–522行、638–641行）。Opus 的默认 PT 是 111，fmtp 为 minptime=10;useinbandfec=1;stereo=1（236–241行），与摘录一致。示例 offer 列出的是 PT 8 的 PCMA 和 PT 101 的 telephone-event。诊断 answer 只列出了 111 opus，没有 8 或 101。RFC 3264 §6.1 要求 recvonly 的 answer 至少包含 offer 里的一种格式，可以额外再列自己的格式。这条诊断 answer 没有列出 offer 中的格式。库提供 AudioCapability::pcma()（255–264行）。若对端确实是 PCMA，需要自己把 PCMA 写进 media_capabilities。本课没有改官方示例，也没有把“加上 pcma() 之后的新 answer”当成已跑证据。

4. 三条常见 SIP 配方怎么落到 API

README Configuration 给出三条 SIP 配方。本课把它们映射到 API，并用已通过的官方测试核对 SDP 属性。没有在本轮对这三条都做真实 RTP 互发。

对端起点再改本轮用来核对的官方测试
SIP 中继，纯 RTPsip()（不改）rtp_mode_no_ice_dtls_artifacts：RTP/AVP，无 ICE/DTLS 属性
SIP 中继，SDES-SRTPsip()keying = Keying::Sdescreate_offer_srtp_mode_includes_crypto（10926–10949行）：协议为 RTP/SAVP，且存在 a=crypto，套件名前缀为 AES_CM_128_HMAC_SHA1_80。create_answer_srtp_mode_uses_savp_profile（11015–11044行）对 answer 做同样的协议与属性断言
带 ICE 的 SIP 话机（例如 Linphone）sip()connectivity = Connectivity::IceLite，keying = Keying::Sdesrtp_mode_ice_lite_sdp_attributes（13220–13276行）核了 IceLite 仍用 RTP/AVP，并有 a=ice-lite、ufrag、pwd、candidate，且无指纹。完整配方 IceLite×Sdes 由 srtp_mode_ice_lite_answer_has_ice_attributes（14543–14577行）断言 answer 同时含 a=ice-lite、ICE 凭证行、candidate 和 a=crypto
 
// 配方2：SIP 中继，SDES-SRTP
let mut config = RtcConfiguration::sip();
config.keying = Keying::Sdes;

// 配方3：带 ICE 的 SIP 话机
let mut config = RtcConfiguration::sip();
config.connectivity = Connectivity::IceLite;
config.keying = Keying::Sdes;

也可从 RtcConfigurationBuilder::sip() 链式调用 .keying(Keying::Sdes) 和 .connectivity(Connectivity::IceLite)。字段写法见 README 示例，以及 1216–1225行。

RFC 4568 §4 规定 a=crypto 只出现在媒体级，格式为 a=crypto:<tag> <crypto-suite> <key-params>，并且 SDP 本身需要由别的安全协议保护。密钥在 SDP 里是明文材料。课文只用明显无效的占位，如下所示；官方测试里出现过的真实或仿真密钥，本课不转载。

# 仅说明格式，密钥是无效占位，不能用于发送或协商
m=audio [port] RTP/SAVP 8
a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:NOT_A_REAL_KEY

5. 容易误判的边界

  • 官方示例在本提交会断言失败。日志里的 SSRC 0 与官方测试一致。不要改上游示例，也不要把退出 101 当成环境失败。
  • 没有收到音频 RTP。示例注释写明不发送实际 RTP，只睡眠 2 秒（113–121行）。本轮示例在睡眠前就退出；诊断等了 2 秒也没有 Track。示例还写明：Track 应在 SSRC 锁定之后再出现（124–128行）。本轮没有发送真实 RTP，也没有声称锁定成功。
  • Connected 不等于收到媒体。rtp_mode_answerer_connects_on_set_remote 只说明按 offer 的 c=/m= 地址完成了直连设置。
  • 默认能力不含 PCMA。示例 offer 是 PT 8。诊断 answer 列出的是默认 Opus 111。需要 PCMA 时加入 AudioCapability::pcma()。本课没有跑“改完能力之后”的官方示例。
  • 不讲 SIP 信令，不做生产 UA。信令走 rsipstack。本课不写 INVITE、100、200 OK 的事务流程。
  • 3000 端口冲突与本课无关。这个示例不绑定 3000。3000 只出现在过时的 SSRC 区间写法里。
  • DEBUG 里的 candidate 不是 SDP 证据。判断有没有 ICE，看正式 SDP 是否出现 a=ice-ufrag 等属性，或看第4节列出的官方测试。
  • rtp_play 不是本课载体。它也调用 sip()，但发送的是 VP8 视频。

6.2 八道自测

先遮住答案。每题都可单独判断，不需要等待聊天回复下一题。八道答案篇幅相同。

第1题

为什么第20课用 webrtc()，本课改用 sip()？

显示第1题答案

第20课的对端是浏览器，必须用完整ICE和DTLS-SRTP，所以选用webrtc()。本课对端是模拟的SIP音频SDP：无ICE、无crypto，走纯RTP。sip()预设是Sdp×None。不要把上一课的webrtc()配置直接套到这种对端上以便完成对接。

第2题

webrtc() 和 sip() 在源码里差哪几个字段？各自的取值是什么？

显示第2题答案

二者只差选路、密钥、扩展开关、rtcp-mux策略和BUNDLE策略。webrtc()是Ice、Dtls、开扩展、Require、MaxBundle；sip()是Sdp、None、关扩展、Negotiate、Balanced。完整英文字段名以第2节对照表为准。

第3题

在本课固定提交上运行未改的 rtp_track_event，本轮实际结果是什么？

显示第3题答案

固定提交上未改示例在第67行断言失败，退出码是101。set_remote之后receiver.ssrc()是0，并不在2000到2999。没有打印本地answer，没有Track事件，也没有等到2秒结束。因此绝不能把这次运行写成协商成功或已经成功收到媒体包。

第4题

为什么说示例里 2000–2999 的断言已经过时？本课应不应该改上游示例让它变绿？

显示第4题答案

同一提交里add_transceiver把接收SSRC初始化为0。官方测试rtp_mode_track_event_after_set_remote要求：offer没有a=ssrc时，SSRC应保持未知的0。本课不要为了让示例变绿去改上游，该断言已和库不一致。

第5题

README 里三条常见 SIP 对端，分别怎样映射到 API？本课有没有跑过全部 Connectivity × Keying 组合？

显示第5题答案

纯RTP中继直接用sip()。SDES-SRTP中继是sip()再把keying设为Keying::Sdes。带ICE的话机例如Linphone，是sip()再设IceLite和Sdes。库称任意组合都可用，本课只教这三条能在README或测试里对得上的配方。

第6题

这次运行能证明已经收到音频 RTP 吗？Track 事件要等到什么时候？

显示第6题答案

不能。这次运行并不能证明已经收到音频RTP。官方示例写明它不发送实际RTP，只睡眠2秒。本轮示例在睡眠前就崩溃；跳过断言的诊断同样等了2秒也没有Track。Track要等SSRC锁定之后才会出现。Connected或打印了offer，都不等于已经收到音频媒体。

第7题

默认 sip() 去回答示例里那段 PCMA offer 时，要注意什么？

显示第7题答案

默认能力是Opus加PCMU，并不包含PCMA。示例offer是PT 8的PCMA。跳过过时断言后的诊断answer只列出了111 opus，没有8或101。方向是recvonly，协议是RTP/AVP。对端若要用PCMA，必须自行把PCMA加入默认能力列表。

第8题

本课为什么不讲 SIP INVITE？这里的 3000 是端口冲突吗？课文里能不能写真实的 a=crypto 密钥？

显示第8题答案

信令由rsipstack负责，rustrtc只管媒体SDP与RTP。本课不写INVITE流程，也不做生产UA。示例并不监听3000，3000只是过时断言里SSRC区间的开区间末端。crypto行只用明显无效的占位，切勿把真实或仿真密钥写进任何对外公开的课文中。

6.3 间隔回忆与来源

明天先不看代码，写出 webrtc() 与 sip() 各五个差异字段，并画出“模拟 offer → sip() → 本轮示例在 SSRC 断言处退出”的关系。隔一天再对照第13课：同一段 RTP/AVP、无 ICE、无 crypto 的音频 SDP，判断标签是什么，映射到哪个构造函数。可以把你的证据卡发来，再针对实际缺口继续提问，不因课文已经写完就自动记为掌握。

主读源码：rtp_track_event.rs 与 RtcConfiguration::webrtc / sip 964–989行。先读五个差异字段、示例里的模拟 offer 和那条 SSRC 断言，再按需要打开第4节列出的测试，不展开 ICE 实现专题。

其他核对来源：

  • README Configuration：两套预设对照表与三条 SIP 配方。
  • RFC 3264 §6.1：answer 方向、端口为 0 才是拒绝、recvonly 的格式必须含 offer 中的一种。
  • RFC 4568 §4：a=crypto 的媒体级格式；SDP 需要另外的安全保护。
  • RFC 8445 §2.5：ICE-lite 只用 host 候选，应答检查，不主动发起检查。
  • RFC 3550 §3：SSRC 是 RTP 头里的 32 位随机标识，不是 2000–2999 区间。
  • 第13课、第20课：判断方法与 webrtc() 音频接收证据，不把上一课结论抄到这里。
  • 本轮脱敏验证摘要：Linux 教学电脑上的运行与测试结果。不是用户本机运行记录。
