sip() 加上 IceLite 与 Sdes：给带 ICE 的 SIP 话机协商（a=ice-lite 与 a=crypto）

1. 为什么在第22课的 sip()+Sdes 之后还要改 connectivity

第22课的对端是不走 ICE 的 SDES-SRTP：协议 RTP/SAVP，有 a=crypto，没有 a=ice-ufrag / a=candidate。对应配置是 sip() 再只改 Keying::Sdes，选路仍是 Connectivity::Sdp。

配方3的对端是带 ICE 的 SIP 话机。密钥还是按 RFC 4568 用 a=crypto 交换，但媒体路径要按 ICE 来找：本端做 ICE-lite，应答对端全量 ICE 的连通性检查并跟随其提名。所以起点还是 sip()，这一次要改两个字段：connectivity = Connectivity::IceLite 与 keying = Keying::Sdes。不要只用第22课的配置去对接这类话机，也不要把配方3改成 webrtc()——那是全量 Connectivity::Ice 加 Keying::Dtls，不是本课。

README 把这条写成：“SIP phone with ICE (e.g. Linphone)” 从 sip() 起步，然后 connectivity = Connectivity::IceLite，keying = Keying::Sdes。出处：README Configuration 配方表第246行。

sip() 本身不会替你改这两个字段，它的预设仍是 Sdp × None：

    /// For a SIP peer (a trunk, a phone, a PBX): the address of its SDP (no
    /// ICE), plain RTP, no WebRTC header extensions, RTCP multiplexing when
    /// the peer accepts it, a transport for each kind of media without
    /// BUNDLE. Change `keying` for SDES-SRTP, `connectivity` for ICE-lite.
    pub fn sip() -> Self {
        Self::new(
            Connectivity::Sdp,
            Keying::None,
            false,
            RtcpMuxPolicy::Negotiate,
            BundlePolicy::Balanced,
        )
    }

摘自 config.rs 977–989行 @ f1b59bf。注释已经写明：Change keying for SDES-SRTP，connectivity for ICE-lite。

2. IceLite 与 Sdes 在 API 和 SDP 里一起改了什么

Connectivity::IceLite 定义在 config.rs 153–155行：ICE-lite（RFC 8445 §2.5），是一种直接传输，应答全量 ICE 对端的检查并跟随其提名。它不是 Connectivity::Ice。Keying::Sdes 仍是第22课那个枚举成员：SDES、a=crypto（RFC 4568）、RTP/SAVP（171–178行）。两种等价写法：

let mut config = RtcConfiguration::sip();
config.connectivity = Connectivity::IceLite;
config.keying = Keying::Sdes;
let config = RtcConfigurationBuilder::sip()
    .connectivity(Connectivity::IceLite)
    .keying(Keying::Sdes)
    .build();

Builder 的 .connectivity(...) 在 config.rs 1216–1220行，.keying(...) 在 1222–1225行，RtcConfigurationBuilder::sip() 在 1127–1132行。扩展开关、rtcp_mux_policy、bundle_policy 都不因这一步而改，仍是 sip() 的预设。

RFC 8445 §2.5 规定：lite 实现只用 host 候选，不主动发起连通性检查，也不跑全量状态机，但必须能应答检查。RFC 8839 §5.3 规定 a=ice-lite 只能出现在会话级，用来声明本端是 lite。源码注释与实现一致：sdp_is_ice_lite 只看会话级（1592–1598行），build_description 把 ice-lite 写进会话属性，把 ice-ufrag / ice-pwd / candidate 写进媒体属性（5881–5913行）。RFC 8839 §5.4 允许 ufrag/pwd 出现在会话级或媒体级；§5.1 规定 a=candidate 只能在媒体级，host 候选必须省略 raddr / rport。

4. 答案怎样同时带上 ICE 与 crypto，本端为什么是 Controlled

配方3要同时做两件事：按第22课的 SDES 规则写出媒体级 a=crypto 和 RTP/SAVP，再按 ICE-lite 写出会话级 a=ice-lite 与媒体级凭证、候选，好让对端的全量 ICE 来检查本端。

RFC 8445 §6.1.1 规定角色：一方是全量实现、一方是 lite 时，全量一方必须是 Controlling，lite 一方必须是 Controlled；lite 只监听并应答检查，再按提名结束 ICE。主测试的远程 offer 没有 a=ice-lite，所以本端作为 IceLite answerer 应取 Controlled。实现上，create_answer 在对端不是 lite 时把角色设为 Controlled（1574–1586行）；IceLite 直接传输在写入对端参数时也会再设一次 Controlled（3457–3466行）。官方测试断言了 pc.inner.ice_transport.role() == Controlled。

SDP 怎么写出来：build_description 在 connectivity == IceLite 时，若会话里还没有 ice-lite 就补上，再把本段的 ufrag、pwd 和候选行写入媒体属性（5881–5913行）。同一份描述里的 a=crypto 仍走第22课已经看过的 SDES 分支，本课不重讲 tag、套件和 MKI 细节。RFC 4568 §4 仍然要求：a=crypto 是媒体级属性，SDP 里的密钥材料必须另有协议保护。

5. 容易误判的边界

  • 不要粘贴真实密钥或 ICE 口令。inline: 后面是明文密钥材料，ice-pwd 是 ICE 口令。公开课文、摘录、证据卡只用 inline:<redacted> 与占位口令。上游测试夹具里出现过的密钥和口令，本课不转载。
  • IceLite 不是全量 ICE。Connectivity::IceLite 是直接传输，应答检查并跟随提名，只用 host 候选。全量收集、主动检查和提名是 Connectivity::Ice，也是 webrtc() 的预设。不要把本课写成已经跑过全量 ICE。
  • Sdes 不是 Dtls，配方3 不是 webrtc()。配方3 只在 sip() 上改 IceLite 与 Sdes。指纹、a=setup 和 DTLS 握手属于 Keying::Dtls。
  • 测试通过不等于已经从话机收到媒体。主路径两个库测试核的是协商字段和 Controlled 角色。没有真实话机，也没有公网。Connected 同样不是话机收包证据。
  • 可选的 ice_lite_sdes 不是 Linphone。它是两个本地 PeerConnection 在回环上互发媒体，配置从 webrtc() 覆盖字段，两端都是 IceLite，不是从 sip() 起步。不要把它写成公网或真实话机成功。
  • 不要宣称九格都跑过。库称任意 Connectivity 可配任意 Keying；那是库的声明。本课只跑了配方3主测试、IceLite+None 对照，以及可选的两端 IceLite × Sdes 回环互发。
  • 没有 rtcp-mux 时，只有 RTP 组件的提名可以选择媒体对。测试 ice_lite_rtcp_component_nomination_keeps_rtp_pair（14580–14696行）的注释写明：Linphone 会对 RTP（组件 1）和 RTCP（组件 2）都做检查并提名；若误把 RTCP 提名当成媒体对，RTP 会从本端 RTCP 端口发出，对端也可能落到 RTCP 端口，按源端口过滤的 NAT 会丢掉这种包。诊断答案在对端没有 a=rtcp-mux 时写出了组件 1 和 2 两条 host 候选，并保留 a=rtcp:。本课没有跑这个测试，它不是主路径。
  • 没有官方示例文件。不要把第21课的 rtp_track_event 或第22课的测试改成 IceLite+Sdes 再当成官方示例。不要为了让某条路径变绿去改上游。
  • 不讲 SIP 信令，不做生产 UA。把 SDP 放进 INVITE / 200 OK 是 rsipstack 和应用的事。SDP 本身还需要另外的安全保护，见 RFC 4568 与 ICE 口令保护。

6.2 八道自测

先遮住答案。每题都可单独判断，不需要等待聊天回复下一题。八道答案篇幅相同。

第1题

为什么第22课只改 keying 还不够，本课还要把 connectivity 改成 IceLite？

显示第1题答案

第22课的sip()+Sdes只改密钥，选路仍是Sdp，其SDP里没有ICE属性。配方3要对带ICE的SIP话机，须从sip()起步再同时设Connectivity::IceLite与Keying::Sdes。不要改回webrtc()，也不要只改其中一个字段。

第2题

配方3的两种 API 写法是什么？examples/ 里有没有对应的官方示例？

显示第2题答案

两种写法等价：先调用sip()再设connectivity为IceLite、keying为Sdes，或用Builder从sip()起再链式设置这两个字段。examples里没有该配方的官方示例。本课可运行的载体是同一提交上的官方库测试，不要为了补示例去改上游。

第3题

本端 answer 或本地 SDP 必须同时出现哪些协商证据？和前两课差在哪？

显示第3题答案

本端生成的SDP必须同时具备会话级a=ice-lite，媒体级ice-ufrag、ice-pwd、candidate和a=crypto，协议为RTP/SAVP。这与第21课无ICE无crypto、第22课有crypto无ICE对照。不要把指纹写成配方3的证据。

第4题

本轮官方库测试在什么时候、以什么结果通过？它们证明了什么、没证明什么？

显示第4题答案

2026年11月27日19:43:51至19:43:52（日本标准时间），Linux教学电脑上两个官方库测试全部通过，退出码是0。主测试断言了ICE与crypto字段以及Controlled角色。stdout未打印密钥或口令。这不是已从话机收到SRTP的证据。

第5题

本端 Ice-lite 为什么是 Controlled？

显示第5题答案

RFC8445第6.1.1节规定：一方全量ICE、一方ICE-lite时，lite须取Controlled。对端无a=ice-lite时，create_answer和IceLite路径都把角色设为Controlled。官方测试已断言本端是Controlled。

第6题

为什么不能把 a=crypto 的 inline 密钥或 ice-pwd 写进公开课文或证据卡？

显示第6题答案

a=crypto的inline参数是明文密钥材料，ice-pwd是ICE口令，两者都写在SDP里，因此必须另用能保密并保护完整性的协议来保护整份描述。课文、摘录和证据卡只使用inline:<redacted>和口令占位。切勿把真实或夹具密钥、口令写进公开材料。

第7题

IceLite 是不是全量 ICE？配方3 是不是 webrtc()？Sdes 是不是 Dtls？

显示第7题答案

Connectivity::IceLite不是全量ICE，也不会变成webrtc()那套Ice加Dtls。Keying::Sdes靠媒体级a=crypto换密钥，不是靠指纹和DTLS握手。配方3仍从sip()起步只改这两个字段。也不要把九格组合都写成已经跑过。

第8题

ice_lite_sdes 或库测试通过，是不是已经从 Linphone 或真实话机收到了 SRTP？

显示第8题答案

可选的ice_lite_sdes是两个本地PeerConnection在回环上互发媒体，配置从webrtc()改字段，不是从sip()起步，也不是Linphone或公网。主路径测试只核协商字段与角色。测试通过或Connected，不等于已经从话机收到SRTP。
