ICE 基础流程：从候选到选路

一句话：先找可能的地址，再实际发包检查，最后统一选一条路。 ICE 不负责传递信令，也不加密音频。这是基础流程笔记，不是高级调参课。

收集候选 → 经应用信令交换 → 候选配对 → STUN 连通性检查
→ 得到有效候选对 → controlling 提名 → 选定路径 → 媒体传输与保活

1. 为什么需要 ICE

A 家的 192.168.1.10:5000 不是互联网上可直接路由到的地址，B 家也可能用同一个私网地址。NAT 会改写包的来源 IP/端口，并按规则放行回包。知道一个地址不等于知道它能不能通，ICE 用实测来选路。RFC 8445 §2

2. 收集候选：我可能从哪里被联系到

  • host：本机接口上绑定的 IP 和端口；同一局域网里可能直接可达。
  • srflx：从本地 UDP socket 向 STUN 服务器查询，得到服务器看到的映射 IP/端口。查到地址不保证对端能打进来。
  • relay：向 TURN 申请的中继地址；发到这里的数据由 TURN 转发。
  • prflx（附注）：检查时才发现、原先没列出的地址，不是靠问 STUN 服务器预先获得的。

纠正前面的简化说法：relay 通常在收集阶段就准备好，并参与候选对检查，不是所有直连超时后才开始申请。 srflx 检查失败也不等于必然只能 relay，检查中新发现的 prflx 也可能有帮助；能否直连取决于双方 NAT/防火墙行为，不作“家用路由器一定能通”的保证。RFC 8445 §5.1.1、§7.3.1.3

3. 交换信息，再组成候选对

应用通过自己的信令通道交换：候选、ice-ufrag（用户名片段）和 ice-pwd（ICE 密码）。常见载体是 SDP；ICE 本身不负责把 SDP 送给对方。信令应可信并受保护；ICE 密码不是媒体加密密钥。

把“我的本地候选”和“对方的远端候选”配成兼容的候选对，按规则安排检查。例如：A 的 host ↔ B 的 srflx。不是看到一个公网地址就认定成功。RFC 8445 §2.3、§6.1.2.2

4. A/B 示例：不是问服务器，而是互相发检查包

以下 IP、端口和字段均为虚构教学示意，不是真实抓包。 假设这次检查中 NAT 保持下列映射，且允许包通过：

A：192.168.1.10:5000 → 203.0.113.10:42000
B：192.168.2.20:6000 → 198.51.100.20:53000

A                         应用信令                         B
|------ 交换候选、ufrag/pwd（不走下面的检查通道） -----------|
|                                                         |
|-- Binding Request → B 的候选 198.51.100.20:53000 -------->|
|    A 仍用收集该候选时的 UDP socket                       |
|    B 实际看到来源：203.0.113.10:42000                     |
|<-- Binding Success Response ----------------------------|
|    B 回到实际来源地址，不是照抄信令里的 A 地址            |
|                                                         |
|    A 校验响应，通过后得到有效候选对                      |
|    B 也会发自己的检查；不是双方都只等别人先发            |

准确一点：直连检查从本地候选关联的 base（底层本地 socket） 发往远端候选；srflx 地址不是另绑一个 socket。临时新开 socket 可能产生不同 NAT 映射，不能代表原候选。relay 检查则经 TURN 转发，并非从中继 IP 在本机直接发包。B 的 ICE 程序回复，路由器只做 NAT/放行，不代替 B 回应。RFC 8445 §2.2、§7.2.4、RFC 8489 §6.3.1

5. Binding 请求里有什么

它是二进制 STUN 报文，不是 HTTP。下列只是可读字段示意，省略了编码细节，没有伪造 MAC 值；假设 A 为 controlling：

A → B：Binding Request
  Type                 0x0001
  Length               后续属性字节数（不含 20 字节固定头）
  Magic Cookie         0x2112A442
  Transaction ID       本次事务的 96 位随机编号
  USERNAME             B的ufrag:A的ufrag
  PRIORITY             用于可能发现的 prflx 候选的优先级
  ICE-CONTROLLING       A 的角色及 64 位冲突裁决值
  MESSAGE-INTEGRITY    用 B 的 ICE 密码计算的 HMAC（值省略）
  FINGERPRINT          STUN 报文 CRC 校验（值省略）

B → A：Binding Success Response
  Type                 0x0101
  Transaction ID       与请求相同
  XOR-MAPPED-ADDRESS   B 实际看到的 A 来源 IP/端口
  MESSAGE-INTEGRITY    本次事务仍用 B 的 ICE 密码（值省略）
  FINGERPRINT          STUN 报文 CRC 校验（值省略）

B 用自己的 ICE 密码校验请求；A 收到响应后匹配事务编号、验证 MESSAGE-INTEGRITY，并检查地址等条件，不是“随便回个包就算通”。无响应时按规则重传，最终可能超时失败。

两个 fingerprint 不要混： STUN 的 FINGERPRINT 是 CRC-32 衍生的报文校验，不是安全认证，也不是 SDP 的 a=fingerprint（DTLS 证书哈希）。完整性认证由 MESSAGE-INTEGRITY 承担；这仍依赖可信的信令交换。

字段依据：RFC 8489 §5、§14.5、§14.7；ICE 属性与验证：RFC 8445 §7.2.1、§7.2.2、§7.2.5。

6. 检查成功 ≠ 最终选路

有效成功响应说明：这次请求从 A 到了 B，响应也回到了 A。它不保证以后一直畅通，也不保证大包、媒体质量或编解码正常。

若有多对能通，由 controlling 方挑有效对，再发带 USE-CANDIDATE 的 Binding 请求进行提名；controlled 方按规则接受、完成检查并确认。提名成功后，双方使用选定对，而不是各自随意选一条。RFC 8445 §7、§8.1.1

7. 选路之后：音频加密与静音保活

浏览器 WebRTC 音频通常接着在选定路上做 DTLS 握手、导出 SRTP 密钥，再用 SRTP/SRTCP 保护 RTP/RTCP。ICE 找路，TURN 转发，二者都不自动加密媒体；音频包不是套在 DTLS 记录里传。RFC 5764 §3

静音不等于挂断。没有 RTP 时仍需要保活维持 NAT 映射；WebRTC 还需持续检查对端是否同意接收。能通过一次检查，不代表可以永远不检查。RFC 8445 §11、RFC 7675 §5.1

最后分清三件事

  • STUN 查地址：我问服务器“你看到我来自哪里”；服务器不转发后续音频。
  • STUN 连通性检查：我直接检查对方的候选；回包的是对方 ICE 程序。
  • TURN 转发：选中中继路径后，TURN 真正收包、转包；不等于媒体加密。

学习补充：SDP、Trickle 与音频路径

SDP 描述，信令交换，ICE 选路，SRTP 保护音频包。 SDP 除了候选和 ICE 凭证，还描述媒体类型和编码；把 SDP 送到对方的是应用信令，例如 SIP 消息或 WebSocket 消息，不是 SDP 自己发包。candidate 仅表示“可以试试”，不是“已经检查成功”。RFC 8839 §4.2.1

Trickle 的多次发送

初始 offer/answer 后，应用继续通过信令发送新增候选，不必为每条候选重新进行 offer/answer。sdpMid 关联 SDP 的 a=mid，标识属于哪个媒体段；usernameFragment 关联 ice-ufrag，用于区分 ICE 的哪一轮，不能拿旧轮次的延迟候选混入重启后的会话。它们不是一回事，也不是固定由 ICE 规定的 JSON 格式。RFC 8838 §9、RFC 5888 §4

应用信令示意（不是抓包，也不是固定消息格式）：
A → B：offer（描述媒体、ICE 凭证及已有候选）
B → A：answer
A → B：新候选①（对应的 mid、ICE ufrag）
A → B：新候选②（同一轮，不重新 offer/answer）
B → A：新候选①
A → B：本轮候选收集结束

接收端若尚未设置对应的远端 SDP，应用先暂存候选，待能关联媒体段和 ICE 轮次后再交给 ICE；这是信令程序需要处理的时序，不是让 STUN 服务器替应用通知对方。

检查之后，RTP 发到哪里

双方成功协商使用 ICE，且产生选定候选对后，媒体栈按选定对发送，不是盲用 c= 地址和 m= 端口；两者的值也可能恰好相同。仅本端打开 ICE，并不代表对端支持。没有协商 ICE 的普通 SIP RTP，通常仍按 SDP 的 c=/m= 发送。RFC 8445 §12.1、RFC 8839 §4.3.3

检查和媒体沿用该候选关联的 UDP socket/base，不能检查后随便换一个端口，期待 NAT 映射仍有效；relay 则经 TURN 转发。STUN 是协议，不等于公共 STUN 服务器：双方即使没配公共 STUN 服务，也能在 host 候选之间直接收发 Binding 检查。RFC 8445 §2.2、§7.2.4

凭证和角色

假设用户名片段仅作示意，不是真实凭证：A123、B456
A → B：USERNAME = B456:A123；用 B 的 ICE 密码计算校验
B → A：USERNAME = A123:B456；用 A 的 ICE 密码计算校验

记法：接收方 ufrag 在前，用接收方密码。ICE 密码验证检查报文，不加密音频，仍依赖可信信令保护。RFC 8445 §7.2.2

完整 ICE 的两端都会主动检查，controlled 不是“只回复”；仅 controlling 负责最终提名。例外是 ICE-Lite：只响应检查，不主动发检查；与 full ICE 互通时由 full 端 controlling、主动检查并提名，哪怕 full 端是 SDP answerer。RFC 8445 §2.5、§6.1.1

静音、重启和媒体安全的边界

  • 静音可能没有 RTP，但不能仅据此认定断线。NAT 保活维持映射；consent freshness 确认对端仍同意接收，是相关但不同的机制。RFC 8445 §11、RFC 7675 §5.1
  • ICE restart 更换 ice-ufrag 和 ice-pwd，通过信令交换后重新检查、提名；真换网必须有适用于当前网络的候选，光告诉对方新 IP 不保证恢复。RFC 8445 §9、RFC 8839 §4.4.1.1.1
  • 协议要求与实现不要混：rustrtc e13b5f2 的 restart 只换凭证，保留候选和 socket（src/transports/ice/mod.rs:1646–1652）；不能据此声称它自动重采新网卡候选。其保活也不能等同完整 RFC 7675 consent 实现（见第 3 课核查）。
  • WebRTC 主线：SDP 交换 → ICE 检查/提名 → DTLS 导出密钥 → SRTP 音频。纯 RTP 不需 DTLS，SDES-SRTP 从 SDP 协商密钥，也不需 DTLS；ICE 与密钥交换是两件事。RFC 5764 §3、RFC 4568 §4
  • SRTP 在 RTP 基础上提供加密、完整性认证和防重放，不负责编码声音；ICE 通不代表编码匹配，也不代表 DTLS 已完成。RFC 3711 §3.3、§3.3.2
